## Процесс задачи: от шага к шагу, от агента к агенту

```
 тип задачи T ──▶ процесс P (шаги по порядку)
                       │
┌──────────────────────▼──────┐ делегат = агент шага ┌──────────────────────┐  I1 claim  ┌───────────────┐
│ Задача входит в шаг 1       ├────────────────────▶│ Очередь агента A     ├───────────▶│ Agent Runner  │
│ (колонка шага, агент A)     │  запуск в очереди    │ приоритет, затем     │            │ → агент A     │
└──────────────▲──────────────┘                      │ время; аренда        │            └───────┬───────┘
               │                                     └──────────────────────┘                    │ I2 итог
               │ при неудаче и попыток < max_runs (3): повтор шага                               │
               │                                                                                 ▼
               │                                     ┌──────────────────────────────────────────────┐
               └─────────────────────────────────────┤ ICPlan применяет правила шага к итогу:        │
                                                     │ успех → (require_review: ждать «принято»)     │
┌─────────────────────────────┐   переход при успехе │ неудача → переход при неудаче / повтор        │
│ Задача в шаге 2 (агент B)   │◀─────────────────────┤ попытки исчерпаны → ждёт человека             │
│ B читает итог A (M2) и M3   │                      └──────────────────────────────────────────────┘
└─────────────────────────────┘
```

Колонку задачи в процессе меняет **ICPlan** по итогу запуска и правилам шага (FR-197). Агент тулом `update_issue` колонку не меняет. Процесс настраивает пользователь в ICPlan, в коде он не зашит (FR-196).

## Что есть / что нет

✅ есть · ⚠️ частично · ❌ нет

| Механизм | ICPlan | Где в коде |
|---|---|---|
| Запуск при смене делегата | ✅ | `issues/service.ts` → `enqueueDelegateRun` |
| Запуск по упоминанию `@агент` | ✅ | `agents/core` |
| Автоназначение исполнителя на колонку | ⚠️ только «Исполнитель», без запуска | `columns/service.ts` (`autoAssignUserId`) |
| Процесс по типу задачи, шаги, переходы по итогу | ❌ — доработка AD-17 (задачи 3.1, 3.6) | — |
| Очередь агента с арендой | ✅ | `/agent-runs/claim`, `AGENT_RUN_LEASE_SECONDS` |
| Эффект Действия «делегировать агенту» | ❌ — доработка (T-04) | `actions` |
| Проверка человеком и вердикт | ❌ — доработка (FR-199, FR-200) | — |
| Передача итога следующему агенту | ⚠️ комментарии; M2 и M3 — через Memory | — |

## Блоки

| Блок | Задача | Нужен? |
|---|---|---|
| Процесс типа задачи | тип задачи задаёт шаги | Да — ядро автоматизации (FR-189, FR-196) |
| Шаг процесса | колонка + агент + переход при успехе и при неудаче + `max_runs` + `require_review` | Да (FR-188) |
| Переход по итогу | ICPlan двигает задачу по правилам шага | Да (FR-197) |
| Очередь агента | приоритет, затем время; аренда | Да (FR-198) |
| Эффект Действия | гибкие условия: метка, поле | Да (FR-190) |
| Защита от дублей | один активный запуск на задачу и агента | Да (FR-192) |

## Плюсы / минусы по модулям

| Модуль | ➕ | ➖ |
|---|---|---|
| Процесс типа задачи | процесс виден на доске и меняется без кода | только линейные шаги; ветвления — пересмотр |
| Переход по итогу | одно место решения, агент не двигает задачу | правила шага надо настроить |
| Лимит попыток | нет бесконечного цикла между шагами | после лимита задача ждёт человека |
| Эффект Действия | любые условия | сложнее отлаживать цепочки |
| Защита от дублей | нет двойной работы и трат | нужен явный повтор |
