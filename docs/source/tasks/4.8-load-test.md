## Зачем

Профиль нагрузки — гипотеза; без замера нельзя выпускать в продуктив и настраивать лимиты.

## Что сделать

- Сценарии k6: UI ICPlan, опрос Runner, события, вызовы LiteLLM (mock)
- Замер `kubectl top`, p95, RPS, ошибки
- Сравнение с профилем, обновление R&D и лимитов

## Приёмка

- [ ] Отчёт: p95 API < 300 мс при 20 RPS
- [ ] Потребление узла записано
- [ ] Профиль в R&D обновлён
- [ ] Нагрузка достигла профиля модуля → потребление в пределах ёмкости узла 8 vCPU / 32 ГБ / 400 ГБ, запуски в очереди не теряются; нагрузка выше профиля → очередь или отказ с причиной, поды не выходят за limits; замер 4.8 → фактические значения записаны и сравнены с профилем (NFR-1, NFR-2, NFR-3, NFR-4, NFR-5, NFR-6, NFR-7, NFR-8, NFR-9, NFR-10, NFR-13, NFR-14)
- [ ] 15 пользователей ICPlan и 4 запуска → p95 API < 300 мс, запуски не теряются; 12 запусков «coder» → лишние в очереди, узел не уходит в нехватку памяти; замер перед продуктивом → p95, RPS и потребление записаны, гипотезы профиля обновлены; больше 6 запусков «coder» или упор в RAM → шаг роста: узел для `itsaplan-agents` с taint (NFR-11)
- [ ] Пик профиля (~20 RPS, до 6 запусков) → ~13 ГБ RAM и ~5 vCPU в ёмкости узла; нагрузка вдвое выше → поды в limits, предупреждение эксплуатации до отказа; замер 4.8 → значения записаны и сравнены с профилем (NFR-12)
