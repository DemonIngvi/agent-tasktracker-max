# PRD: Agent TaskTracker Max

> Перенесено из `agent-architecture` скриптом `tools/migrate.py`. Код требования в исходных спеках указан у каждого FR.

## 0. Document Purpose

Документ для владельца продукта, архитектора и разработчиков. Требования сгруппированы по исходным спекам и пронумерованы сквозным образом.

## 1. Vision

Нужна расширяемая платформа для запуска LLM-агентов: агенты добавляются и настраиваются конфигом, без кода; модели, тулы, MCP, промпты, скиллы и память управляются централизованно; каждый запуск изолирован; расход токенов и безопасность контролируются в одной точке. Платформа должна встраиваться в ICPlan, который назначает агента на задачу.

## 2. Target User

### 2.1 Jobs To Be Done

- **Пользователь ICPlan:** быстро получить результат без ручной передачи между этапами; видеть ход работы.
- **Владелец продукта:** предсказуемые сроки и затраты, ценность для пользователей.
- **Администратор платформы:** чтобы агенты делали только разрешённое и не тратили лишнего.
- **Эксплуатация (DevOps):** стабильность, бэкапы, понятные отказы.
- **Безопасность:** нет утечек, минимальные права, аудит.
- **Тестировщик / QA:** проверяемые требования, воспроизводимые среды.
- **Агент-исполнитель:** завершить задачу с первого раза, иметь нужный контекст и доступы.
- **Агент-ревьюер:** видеть полный результат и контекст.

## 3. Glossary

- **Harness** — Агентский цикл на LangGraph: контекст → LLM → тулы, hooks, пауза на approve, возобновление, стрим шагов.
- **ICPlan** — Таск-трекер It's a Plan: доска, процессы, настройка агентов, очередь запусков, UI задачи. Уже есть, дорабатываем.
- **Инфраструктура** — Кластер k3s, Helm, Traefik ingress, PostgreSQL (CloudNativePG) с PgBouncer, RustFS, секреты, бэкапы, сетевые политики, профиль нагрузки.

- **M3Record** — состояние задачи и передача следующему шагу (FR-39, AD-20)

## 4. Features

### 4.1 icplan-integration

**Description:** Контракт уровня C1 между ICPlan и Agent Platform: ICPlan ставит запуски в свою очередь, Agent Runner забирает их как внешний раннер (pull), стримит шаги и итог обратно, получает решения пользователя. Обоснование: R&D.

**Functional Requirements:**

#### FR-1: Агент платформы как внешний агент ICPlan

Агент, исполняемый платформой, SHALL быть заведён в ICPlan с типом «внешний»; его запуски MUST исполняться только Agent Runner по API-ключу агента.

Код в исходной спеке: `R-ICP-01`.

**Consequences (testable):**
- Делегирование агенту платформы: когда пользователь делегирует задачу внешнему агенту платформы, тогда запуск появляется в очереди ICPlan и забирается Agent Runner.
- Внутренний агент: когда задача делегирована внутреннему агенту ICPlan, тогда запуск исполняет ICPlan, Agent Runner его не забирает.
- Неверный ключ агента: когда Agent Runner опрашивает очередь с отозванным ключом, тогда ICPlan отвечает отказом в доступе, запуски не выдаются.

#### FR-2: Получение запуска из очереди (pull)

Agent Runner SHALL получать запуски, опрашивая очередь ICPlan; ICPlan MUST NOT вызывать платформу напрямую.

Код в исходной спеке: `R-ICP-02`.

**Consequences (testable):**
- Платформа недоступна: когда Agent Runner остановлен, а задача делегирована, тогда запуск ждёт в очереди и исполняется после запуска Runner.
- Пустая очередь: когда в очереди нет запусков, тогда Runner ждёт интервал опроса и повторяет запрос без ошибок.
- ICPlan недоступен: когда очередь ICPlan не отвечает, тогда Runner повторяет опрос с растущей задержкой и пишет событие о недоступности.

#### FR-3: Однократная выдача запуска

Запуск SHALL выдаваться одному экземпляру Runner; повторный опрос MUST NOT приводить к двойному исполнению.

Код в исходной спеке: `R-ICP-03`.

**Consequences (testable):**
- Два Runner опрашивают одновременно: когда два экземпляра Runner опросили очередь в один момент, тогда запуск получил ровно один из них.
- Runner упал после получения: когда Runner получил запуск и упал до старта, тогда по истечении аренды запуск возвращается в очередь и выдаётся снова.
- Повторный опрос того же Runner: когда Runner повторно опрашивает очередь с уже взятым запуском, тогда второй раз этот запуск не выдаётся.

#### FR-4: Стрим шагов и итог в задачу

Runner SHALL передавать в ICPlan шаги запуска по мере работы и итог; итог MUST публиковаться в задаче комментарием от имени агента, вложения — в задачу.

Код в исходной спеке: `R-ICP-04`.

**Consequences (testable):**
- Итог с вложением: когда агент завершил работу с файлом-результатом, тогда в задаче комментарий агента и вложение.
- Итог без вложений: когда агент завершил работу текстовым итогом, тогда в задаче один комментарий агента.
- Обрыв стрима: когда соединение со стримом прервалось посреди запуска, тогда Runner дошлёт пропущенные шаги по порядковым номерам, дубли не появляются.

#### FR-5: Подтверждения и ответы

ICPlan SHALL показывать в задаче запрос агента на подтверждение действия или вопрос и передавать решение пользователя в Runner.

Код в исходной спеке: `R-ICP-05`.

**Consequences (testable):**
- Подтверждение действия: когда агент ждёт подтверждения и пользователь нажал «одобрить», тогда действие выполняется, запуск продолжается.
- Отказ: когда пользователь нажал «отклонить», тогда агент получает отказ и продолжает без этого действия или завершает запуск.
- Нет прав на подтверждение: когда участник без права подтверждения нажимает «одобрить», тогда решение отклоняется, запрос остаётся открытым.

#### FR-6: Уведомление о решении пользователя

Когда агент ждёт подтверждения или ответа, ICPlan SHALL уведомить исполнителя задачи (и участников с правом подтверждения) и показать срок ожидания; повторное уведомление MUST NOT отправляться чаще, чем раз в заданный интервал. Источник: US-ICP-03.

Код в исходной спеке: `R-ICP-06`.

**Consequences (testable):**
- Запрос подтверждения: когда агент перешёл в ожидание подтверждения, тогда исполнитель задачи получает уведомление со ссылкой на задачу и сроком.
- Нет исполнителя: когда у задачи нет исполнителя, тогда уведомление получают участники с правом подтверждения в проекте.
- Повтор уведомления: когда решение не принято, а интервал повтора не истёк, тогда второе уведомление не отправляется.

#### FR-7: Отмена из ICPlan

Отмена запуска в ICPlan SHALL останавливать его в платформе со статусом `canceled`.

Код в исходной спеке: `R-ICP-07`.

**Consequences (testable):**
- Отмена: когда пользователь отменяет запуск, тогда Runner останавливает Harness и уничтожает sandbox.
- Отмена завершённого запуска: когда пользователь отменяет уже завершённый запуск, тогда статус не меняется, пользователь видит сообщение.
- Отмена во время ожидания подтверждения: когда запуск ждёт approve и его отменяют, тогда запуск завершается `canceled`, запрос подтверждения закрывается.

#### FR-8: Каталог агентов платформы

ICPlan SHALL показывать агентов платформы в общем списке агентов с их описанием и статусом в сети.

Код в исходной спеке: `R-ICP-08`.

**Consequences (testable):**
- Runner не в сети: когда Agent Runner не опрашивает очередь дольше порога, тогда агенты платформы отмечены «не в сети».
- Runner в сети: когда Runner опрашивает очередь, тогда агенты платформы отмечены «в сети».
- Агент выключен: когда агент выключен (`agent.enabled = false`, FR-11), тогда в списке помечен «выключен», делегирование отклоняется с причиной.

#### FR-9: Версия протокола

Протокол раннера SHALL иметь версию; несовместимые изменения MUST выпускаться новой версией, Runner MUST сообщать поддерживаемую версию.

Код в исходной спеке: `R-ICP-09`.

**Consequences (testable):**
- Несовместимая версия: когда ICPlan обновлён до протокола, который Runner не поддерживает, тогда Runner не забирает запуски и сообщает о несовместимости.
- Совместимая версия: когда версии протокола ICPlan и Runner совпадают, тогда запуски выдаются как обычно.
- Минорное обновление: когда ICPlan добавил необязательное поле в протокол, тогда Runner продолжает работать, поле игнорируется.

#### FR-10: Указания пользователя во время запуска

Сообщение пользователя агенту по задаче (чат, комментарий с упоминанием, бот), пока у агента активный запуск по ней, ICPlan SHALL прикреплять к этому запуску, а не создавать новый. Runner SHALL получать такие сообщения в ответе heartbeat и передавать в Harness; доставка MUST подтверждаться в истории задачи.

Код в исходной спеке: `R-ICP-16`.

**Consequences (testable):**
- Сообщение во время работы: когда пользователь пишет агенту «добавь тесты», запуск активен, тогда сообщение прикреплено к запуску, Runner получает его со следующим heartbeat, в истории «получено агентом».
- Запуск завершён: когда сообщение пришло после завершения запуска, тогда создаётся новый запуск с контекстом чата.
- Стоп: когда пользователь пишет «стоп», тогда запуск завершается с итогом сделанного.

#### FR-11: Выключение агента

Агент SHALL иметь признак «включён». У выключенного агента ICPlan MUST NOT создавать запуски и выдавать раннеру запуски из очереди; запуски в очереди ждут включения. Активные запуски при выключении доделываются или отменяются — по выбору администратора.

Код в исходной спеке: `R-ICP-17`.

**Consequences (testable):**
- Выключение: когда администратор выключил агента, активные — «доделать», тогда активные завершаются, новые не создаются, у задач причина «агент выключен».
- Отмена активных: когда при выключении выбрано «отменить», тогда активные запуски отменены, Runner узнаёт по heartbeat.
- Включение: когда агента включили, тогда запуски из очереди выдаются по порядку.

#### FR-12: Проверка агента в чате

Администратор SHALL проверять агента в чате с ним (тред агент × пользователь, без задачи): Runner обслуживает канал чата ICPlan, агент работает по своему определению. Изменение задач из тестового чата MUST требовать подтверждения в чате; для теста SHALL быть доступна mock-модель.

Код в исходной спеке: `R-ICP-18`.

**Consequences (testable):**
- Тест в чате: когда администратор пишет агенту в чате пример задания, тогда агент отвечает, шаги и тулы видны в чате, задачи не меняются.
- Попытка изменить задачу: когда агент в тестовом чате вызывает тул изменения задачи, тогда запрос подтверждения в чате; без него изменение не выполняется.
- Mock-модель: когда в тесте выбрана mock-модель, тогда ответы по сценарию mock, затрат нет.

#### FR-13: Очистка запусков и переписки по сроку

ICPlan SHALL удалять задачей worker форка завершённые запуски `agent_run` старше `runs.retention_days` (по `finished_at`) и треды чата агента старше `chat.retention_days` (по `updated_at`) вместе с сообщениями и событиями. Запуски, у которых ещё есть события `run_event`, MUST пропускаться; `issue_activity` MUST NOT удаляться по времени. Значение 0 отключает очистку (AD-25).

Код в исходной спеке: `R-ICP-19`.

**Consequences (testable):**
- Очистка запусков: когда завершённый запуск старше `runs.retention_days` и событий `run_event` у него нет, тогда worker удаляет строку `agent_run`.
- У запуска остались события: когда запуск старше `runs.retention_days`, но у него ещё есть `run_event`, тогда запуск пропускается до следующей очистки.
- Очистка переписки: когда тред чата агента не обновлялся дольше `chat.retention_days`, тогда worker удаляет `agent_chat_thread` вместе с его сообщениями и событиями.
- История задачи остаётся: когда worker удалил треды чата старше `chat.retention_days`, тогда комментарии и записи «агент взял / закончил» в `issue_activity` остаются, пока жива задача.
- Очистка отключена: когда `runs.retention_days` или `chat.retention_days` равен 0, тогда worker не удаляет запуски или треды соответственно, сколько бы им ни было.
- Удаление в журнале: когда цикл очистки удалил запуски или треды, тогда в журнал worker записано, сколько строк `agent_run` и `agent_chat_thread` удалено и по какому сроку.
- Сбой очистки: когда удаление не прошло (ошибка БД, внешний ключ), тогда строки остаются, ошибка записана в журнал worker и поднимает уведомление эксплуатации; следующий цикл очистки повторяет удаление.

#### FR-14: Конфигурация модуля

Модуль SHALL брать свои параметры (8, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Изменение настройки SHALL действовать со следующего запуска; обязательные поля MUST проверяться при сохранении.

Код в исходной спеке: `R-ICP-10`.

**Consequences (testable):**
- Значение по умолчанию: когда `agent.kind` (внутренний агент ICPlan или внешний (наш Runner)) не задан в настройках, тогда применяется значение по умолчанию: internal.
- Выше максимума: когда `agent.delegation_delay_sec` задан больше 86400, тогда значение отклонено, ошибка называет `agent.delegation_delay_sec` и границы 0–86400.
- Нет обязательного параметра: когда при старте не задан `protocol.version`, тогда модуль не стартует, ошибка называет `protocol.version`.

#### FR-15: Хранилища данных

Модуль SHALL хранить свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`), S7 (RustFS (S3 API), бакет `planner-attachments`) (`interfaces.md`). Секреты MUST NOT храниться в git и в БД открытым текстом: в БД допускается только шифротекст (ключи агентов `ai_agent.api_key_ciphertext`, учётные данные тулов), ключ шифрования `APP_ENCRYPTION_KEY` MUST храниться вне БД и её бэкапов (Secret кластера).

Код в исходной спеке: `R-ICP-11`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет агенты (вид, ключ, `enabled`), `agent_run` (очередь, аренда, итоги),…, тогда запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`).
- S1 недоступно: когда S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает, тогда выдача запусков и приём итогов останавливаются; Runner повторяет с backoff, итог держит до восстановления.
- Доступ вне своих хранилищ: когда код icplan-integration обращается к таблицам вне S1, S7, тогда доступа нет: роль БД icplan-integration ограничена S1, S7.
- Секрет в БД: когда модуль сохраняет API-ключ агента, тогда в S1 попадает только шифротекст; из дампа БД без `APP_ENCRYPTION_KEY` ключ не прочитать.

#### FR-16: Интерфейсы обмена

Интерфейсы модуля (I1, I2, I3, I19, I20, I21) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-ICP-12`.

**Consequences (testable):**
- Таймаут I1: когда ICPlan Run Queue → Agent Runner (I1) не ответил за 10 с, тогда вызов прерывается; повтор: backoff до 60 с.
- Права по I20: когда пользователь без права изменения меняет агенты (вид, ключ, `enabled`), `agent_run` (очередь, аренда, итоги), сообщения чата агента, тогда API ICPlan отклоняет запрос (403), данные не меняются, событие в журнале.
- Повтор I2 без дублей: когда вызов I2 повторён после сбоя, тогда дубля нет: да, по (run_id, seq).

#### FR-17: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-ICP-13`.

**Consequences (testable):**
- Runner не в сети: когда runner не в сети, тогда агенты платформы «не в сети», запуски ждут.
- Несовместимая версия протокола: когда несовместимая версия протокола, тогда Runner не берёт запуски.
- Объектное хранилище недоступно: когда объектное хранилище RustFS недоступно, тогда итог публикуется без вложений, повтор загрузки.

#### FR-18: Развёртывание

Модуль SHALL разворачиваться так: ICPlan: Deployment `web` (1–2), `api` (2), `worker` (1), `bot` (1) в `itsaplan-core`; вход — Traefik Ingress (HTTPS). Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-ICP-15`.

**Consequences (testable):**
- Установка в составе ICPlan: когда разворачивается релиз ICPlan (ICPlan: Deployment `web` (1–2), `api` (2), `worker` (1), `bot` (1) в `itsaplan-core`; вход — Traefik Ingress (HTTPS)) с модулем icplan-integration, тогда миграции icplan-integration применены до старта `api`, модуль доступен в ICPlan.
- Обновление: когда выходит новая версия форка ICPlan с изменениями icplan-integration, тогда миграции icplan-integration обратно совместимы, `api` обновляется по одной реплике без простоя.
- Откат: когда версия с изменениями icplan-integration не прошла проверки готовности, тогда Helm откатывает ревизию, данные icplan-integration сохранены.

### 4.2 agent-harness

**Description:** Рантайм внутри sandbox, который выполняет агентский цикл (контекст → LLM → тул → результат) и навязывает агенту правила платформы через hooks и policy. Обоснование: R&D.

**Functional Requirements:**

#### FR-19: Инициализация из определения агента

Harness SHALL собирать агента из определения: системный промпт, скиллы, доступные тулы/MCP, профиль памяти, лимиты.

Код в исходной спеке: `R-HRN-01`.

**Consequences (testable):**
- Старт агента: когда Agent Runner запускает Harness с определением агента и задачей, тогда агенту доступны только тулы и скиллы из его определения.
- Битое определение: когда определение агента не проходит схему, тогда Harness не стартует цикл и завершает запуск с ошибкой `invalid_definition`.
- Скилл недоступен: когда скилл из определения не найден, тогда запуск завершается с ошибкой и именем отсутствующего скилла.

#### FR-20: Агентский цикл

Harness SHALL повторять цикл «вызов LLM → выполнение запрошенных тулов → передача результатов в контекст» до завершения, лимита или ошибки.

Код в исходной спеке: `R-HRN-02`.

**Consequences (testable):**
- Вызов тула: когда LLM возвращает запрос вызова тула, тогда Harness выполняет тул и передаёт результат в следующий вызов LLM.
- Ответ без тулов: когда модель вернула финальный ответ без вызова тулов, тогда цикл завершается, итог передаётся дальше.
- Несколько тулов за шаг: когда модель запросила два тула в одном ответе при `model.parallel_tool_calls: true`, тогда оба проходят G2 по очереди и выполняются, результаты возвращаются в одном следующем шаге; при `false` (по умолчанию) модель запрашивает по одному.

#### FR-21: Вызов LLM только через шлюз

Harness MUST вызывать модели только через LLM Gateway.

Код в исходной спеке: `R-HRN-03`.

**Consequences (testable):**
- Прямой вызов провайдера: когда код в sandbox пытается обратиться к провайдеру LLM напрямую, тогда вызов недоступен (заблокирован сетью sandbox).
- Вызов через шлюз: когда Harness вызывает модель по алиасу, тогда запрос уходит в LiteLLM с ключом агента.
- Шлюз недоступен: когда LiteLLM не отвечает, тогда повтор с задержкой; после лимита ошибок — завершение `failed`.

#### FR-22: Hooks

Harness SHALL предоставлять точки расширения: before/after LLM call, before/after tool call, on_stop. Hook SHALL иметь возможность модифицировать или отклонить действие.

Код в исходной спеке: `R-HRN-04`.

**Consequences (testable):**
- Отклонение тула хуком: когда hook `before_tool` отклоняет вызов, тогда тул не выполняется, агент получает сообщение об отказе.
- Hook изменил аргументы: когда hook `before_tool` нормализует путь в аргументах, тогда тул вызывается с изменёнными аргументами, изменение видно в событии.
- Ошибка в hook: когда hook упал с исключением, тогда действие отклоняется (fail-closed), запуск получает событие об ошибке hook.

#### FR-23: Пауза и возобновление

Harness SHALL уметь приостановить запуск на подтверждение человека (G2) или вопрос пользователю, сохранить состояние и продолжить с того же шага после ответа; после падения процесса запуск SHALL возобновляться с последнего сохранённого шага.

Код в исходной спеке: `R-HRN-05`.

**Consequences (testable):**
- Подтверждение действия: когда hook G2 требует подтверждения, тогда запуск ждёт, после подтверждения продолжает с того же шага без повтора предыдущих.
- Падение процесса: когда процесс Harness упал посреди запуска, тогда новый процесс продолжает с последнего сохранённого шага.
- Истёк таймаут ожидания: когда подтверждение не пришло за `approval_timeout`, тогда действие считается отклонённым, запуск продолжается без него или завершается по политике.

#### FR-24: Стрим шагов

Harness SHALL отдавать события каждого шага по мере выполнения в формате AG-UI (AD-21): перед вызовом тула — реплику агента о намерении, рассуждения модели из `reasoning_content` — событиями `REASONING_*`.

Код в исходной спеке: `R-HRN-06`.

**Consequences (testable):**
- Чат запуска: когда агент вызвал тул, тогда событие о вызове доступно Observability до завершения запуска.
- Порядок событий: когда события пришли с задержкой, тогда получатель упорядочивает их по `seq`.
- Модель без рассуждений: когда провайдер не отдаёт `reasoning_content`, тогда событий `REASONING_*` нет, реплики агента о намерении отдаются.
- Потребитель недоступен: когда Runner временно не принимает события, тогда Harness буферизует их и дошлёт, не теряя шагов.

#### FR-25: Управление контекстом

Harness SHALL удерживать контекст в пределах окна модели, сжимая историю и подгружая память по профилю агента.

Код в исходной спеке: `R-HRN-07`.

**Consequences (testable):**
- Переполнение контекста: когда история превышает порог окна модели, тогда старая часть истории сжимается, ключевые факты сохраняются.
- Короткая история: когда история меньше порога, тогда сжатие не выполняется.
- Сжатие невозможно: когда даже после сжатия контекст не помещается, тогда запуск завершается `limit` с причиной `context_overflow`.

#### FR-26: Quality gate результата

Harness SHALL проверять итог по всем критериям задачи (процесс, человек, агенты — с происхождением; AD-20); исполнитель MUST NOT менять критерии своего шага: формат и обязательные поля — детерминированно (кодом); смысловое соответствие — опциональным валидатором. Результат проверки MUST записываться в итог; при провале — повтор до N раз или завершение со статусом `gate_failed`.

Код в исходной спеке: `R-HRN-08`.

**Consequences (testable):**
- Gate пройден: когда итог содержит все обязательные разделы из критериев, тогда запуск завершается `succeeded`, в итоге отметка «gate пройден».
- Gate не пройден: когда в итоге нет обязательного раздела и повторы исчерпаны, тогда запуск завершается `gate_failed` с перечнем непрошедших критериев.
- Критериев нет: когда у задачи нет критериев приёмки, тогда gate пропускается, в итоге отметка «gate не задан».
- Попытка ослабить критерий: когда агент текущего шага пытается удалить или изменить критерий своего шага, тогда изменение отклонено, событие с причиной.

#### FR-27: Завершение

Harness SHALL завершаться с причиной `done`, `limit`, `gate_failed` или `error` и передавать результат в Agent Runner.

Код в исходной спеке: `R-HRN-09`.

**Consequences (testable):**
- Достигнут лимит шагов: когда агент превысил максимальное число шагов, тогда Harness останавливается с причиной `limit` и частичным результатом.
- Успешное завершение: когда агент вернул итог, тогда статус `done`, итог передан Runner.
- Ошибка модели: когда модель возвращает ошибку после всех повторов, тогда статус `error` с причиной и частичным итогом.

#### FR-28: Указания пользователя в цикле

Harness SHALL принимать сообщения пользователя от Runner во время цикла и добавлять их в контекст на следующем шаге; во время вызова тула — после его завершения. Сообщение «стоп» MUST завершать цикл с итогом сделанного.

Код в исходной спеке: `R-HRN-16`.

**Consequences (testable):**
- Указание: когда во время работы пришло сообщение «используй pytest», тогда на следующем шаге сообщение в контексте, в событиях «учтено».
- Во время тула: когда сообщение пришло во время вызова тула, тогда учитывается после завершения тула.
- Стоп: когда пришло сообщение «стоп», тогда цикл завершается со статусом `done` и итогом сделанного.

#### FR-29: Рабочее пространство в контексте агента

Harness SHALL давать агенту описание рабочего пространства из `RunBundle` (пути, источники, права) и ограничивать файловые и git-тулы путями `/workspace`. В конце запуска Harness SHALL перечислять в `RunResult` опубликованные артефакты: файлы выгруженных папок, ветку и PR.

Код в исходной спеке: `R-HRN-17`.

**Consequences (testable):**
- Описание в контексте: когда запуск стартовал с манифестом из двух источников, тогда агент видит пути и права в контексте.
- Путь вне workspace: когда агент вызывает файловый тул с путём вне `/workspace`, тогда вызов отклонён с причиной.
- Итог: когда агент завершил работу, тогда `RunResult` содержит список артефактов: файлы, ветку, PR.
- Новые зависимости: когда агент изменил lock-файл и вызвал тул `install_dependencies`, тогда Runner повторяет шаг подготовки (AD-19), `/workspace/.deps` обновлён, цикл продолжается.

#### FR-30: Сборка запроса к модели

Harness SHALL собирать запрос к модели из слоёв в порядке: системный промпт платформы → руководство проекта → инструкция и навыки агента → описание тулов и рабочего пространства → контекст памяти → задание запуска → указания пользователя. Параметры модели SHALL браться из таблицы параметров (`model.*`); нижний слой MUST NOT отменять правила системного промпта платформы.

Код в исходной спеке: `R-HRN-18`.

**Consequences (testable):**
- Порядок слоёв: когда стартует запуск агента с руководством проекта и двумя навыками, тогда запрос содержит слои по порядку, у каждого в событиях указан источник и версия.
- Попытка отменить правила: когда инструкция агента или текст задачи требует игнорировать правила платформы, тогда правила системного промпта платформы действуют, событие «конфликт слоёв».
- Параметр не поддерживается моделью: когда у модели нет режима размышлений, а `model.reasoning_effort` задан, тогда LiteLLM отбрасывает параметр (`drop_params`), событие с именем параметра.
- Размышления в бюджете: когда модель вернула токены размышлений, тогда они учитываются в бюджете запуска и затратах; текст размышлений в события не пишется, если `events.level` не «всё».

#### FR-31: Конфигурация модуля

Модуль SHALL брать свои параметры (18, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-HRN-10`.

**Consequences (testable):**
- Значение по умолчанию: когда `model.temperature` (температура выборки) не задан в конфигурации, тогда применяется значение по умолчанию: 0.2.
- Выше максимума: когда `model.temperature` задан больше 1.0, тогда значение отклонено, ошибка называет `model.temperature` и границы 0–1.0.
- Граница от другого параметра: когда `limits.max_tokens` задан больше, чем потолок `budget.per_run_tokens` L0, тогда значение отклонено: `limits.max_tokens` не может быть больше потолок `budget.per_run_tokens` L0.

#### FR-32: Хранилища данных

Harness MUST NOT хранить данные постоянно: рабочие файлы SHALL писаться в S10 среды запуска (владелец — Sandbox), состояние цикла — через API Runner в S5 (I12). Секреты MUST NOT храниться в файлах и контексте.

Код в исходной спеке: `R-HRN-11`.

**Consequences (testable):**
- Состояние цикла: когда Harness сохраняет состояние после шага, тогда checkpoint уходит в Runner по I12 и пишется в S5; на диске среды его нет.
- Перезапуск процесса: когда процесс Harness перезапустился в той же среде, тогда состояние восстанавливается из checkpoint Runner, а не из файлов.
- Файлы результата: когда агент создал файл итога, тогда файл пишется в `/workspace` и перечисляется в `RunResult`, публикацию выполняет Runner.

#### FR-33: Интерфейсы обмена

Интерфейсы модуля (I7, I8, I9, I10, I11, I12) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-HRN-12`.

**Consequences (testable):**
- Таймаут I7: когда Agent Runner ↔ Harness (I7) не ответил за = `timeout_s`, тогда вызов прерывается; повтор: переподключение с последнего `seq`.
- Аутентификация I8: когда собеседник по I8 отклонил учётные данные (bearer virtual key (подставляет…), тогда вызов не повторяется, событие с причиной.
- Неидемпотентный вызов I9: когда вызов I9 (Harness → MCP-серверы) прервался сбоем сети, тогда автоматического повтора нет, решение принимает вызывающий.

#### FR-34: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-HRN-13`.

**Consequences (testable):**
- LiteLLM недоступен: когда litellm недоступен, тогда повтор с backoff; после `circuit.max_errors` — `failed`.
- MCP-сервер недоступен: когда mcp-сервер недоступен, тогда ошибка тула возвращается агенту, цикл продолжается.
- Checkpointer недоступен: когда checkpointer недоступен, тогда пауза на approve невозможна — опасные действия отклоняются.
- Memory API недоступен: когда memory api недоступен, тогда запуск идёт без M3/M2, событие-предупреждение.

#### FR-35: Развёртывание

Модуль SHALL разворачиваться так: процесс внутри контейнера sandbox, образ `ghcr.io/demoningvi/agent-agent-harness:<версия>`; ресурсы — профиль sandbox. Образ закреплён по версии и digest, контейнер создаёт Runner на каждый запуск; ресурсы MUST задаваться профилем sandbox.

Код в исходной спеке: `R-HRN-15`.

**Consequences (testable):**
- Новый образ: когда опубликован новый образ Harness (`HARNESS_IMAGE`), тогда Runner использует его для новых запусков, активные доделываются на прежнем.
- Образ недоступен: когда образ Harness не скачивается из реестра, тогда запуск не стартует, статус `failed` с причиной «образ недоступен», событие эксплуатации.
- Нехватка ресурсов: когда узлу не хватает ресурсов для среды запуска по профилю, тогда запуск ждёт в `queued` до освобождения слотов.

### 4.3 agent-memory

**Description:** Память агентов по видам знания M0–M6: от контекста одного запуска до организационных документов, с понятным моментом записи и местом хранения каждого уровня. Обоснование: R&D.

**Functional Requirements:**

#### FR-36: Уровни памяти M0–M6

Система SHALL поддерживать уровни: M0 рабочая (контекст запуска), M1 сессионная (переписка в треде), M2 эпизодическая (запуски и их итоги), M3 задачная (состояние работы по задаче), M4 семантическая (факты с поиском по смыслу), M5 процедурная (инструкция и навыки), M6 организационная (документы проекта).

Код в исходной спеке: `R-MEM-01`.

**Consequences (testable):**
- Завершение запуска: когда запуск завершён, тогда M0 уничтожается вместе с sandbox, M1–M6 сохраняются.
- Чтение M6: когда агенту нужен документ проекта, тогда он читает его тулом `get_document`, запись в M6 агенту недоступна.
- Неизвестный уровень: когда профиль ссылается на несуществующий уровень, тогда профиль не сохраняется, ошибка валидации.

#### FR-37: Область видимости как атрибут

Каждая запись M1–M6 SHALL иметь область видимости (задача, агент, проект, команда); доступ агента MUST определяться профилем памяти и областью записи.

Код в исходной спеке: `R-MEM-02`.

**Consequences (testable):**
- Чужая область: когда агент без доступа к области «команда» запрашивает такую запись, тогда запрос отклоняется.
- Своя область: когда агент читает M3 своей задачи, тогда запись возвращается.
- Запись в чужую область: когда агент пытается записать в область команды без права, тогда запись отклоняется и попадает в аудит.

#### FR-38: Автоматическая запись M1 и M2

Платформа SHALL сама записывать M1 (каждое сообщение треда) и M2 (старт, итог, ошибка, токены запуска), без участия агента.

Код в исходной спеке: `R-MEM-03`.

**Consequences (testable):**
- Итог запуска: когда запуск завершился, тогда в M2 есть запись с итогом, статусом и токенами.
- Ошибочный запуск: когда запуск завершился ошибкой, тогда в M2 есть запись с ошибкой и причиной.
- Хранилище недоступно: когда БД ICPlan недоступна при записи M2, тогда Runner повторяет отправку итога (`/agent-runs/{id}/result`), ICPlan записывает M2 без дублей по `run_id`.

#### FR-39: Состояние задачи M3

Агент SHALL записывать состояние работы по задаче (сделано, дальше, блокеры) через тул; перед каждым запуском по задаче платформа SHALL добавлять M3 в контекст. M3 шага SHALL содержать передачу следующему: ссылки на артефакты, вопросы, предложенные критерии (AD-20).

Код в исходной спеке: `R-MEM-04`.

**Consequences (testable):**
- Следующий этап: когда агент B берёт задачу после агента A, тогда контекст B содержит M3, записанное A.
- M3 ещё нет: когда первый агент берёт задачу, тогда контекст без M3, агент работает с нуля.
- Конфликт записи: когда два запуска пытаются записать M3 одновременно, тогда сохраняется последняя версия, предыдущая остаётся в истории.

#### FR-40: История запусков в контексте

Перед запуском по задаче платформа SHALL добавлять в контекст краткие итоги последних N запусков этой задачи (M2).

Код в исходной спеке: `R-MEM-05`.

**Consequences (testable):**
- Повторный запуск: когда агент повторно запускается по задаче, тогда видит итоги прошлых запусков.
- Запусков больше N: когда у задачи 10 запусков, N = 3, тогда в контекст попадают итоги трёх последних.
- Нет истории: когда задача запускается впервые, тогда раздел истории в контексте пуст.

#### FR-41: Семантическая память M4 — после MVP

M4 SHALL вводиться вместе с RAG: запись фактов агентом через тул, поиск по смыслу, хранилище — векторное расширение основной БД.

Код в исходной спеке: `R-MEM-06`.

**Consequences (testable):**
- Поиск факта: когда M4 включена и агент ищет факт по смыслу, тогда получает записи из разрешённых ему областей.
- M4 выключена: когда профиль не включает M4, тогда тул поиска по смыслу агенту недоступен.
- Нет результатов: когда поиск не нашёл похожих фактов, тогда агент получает пустой ответ без ошибки.
- Противоречащий факт: когда агент записывает факт, противоречащий факту в той же области, тогда старый факт помечается устаревшим со ссылкой на новый, поиск выдаёт новый.
- Срок действия: когда у факта истёк срок «действует по», тогда поиск по умолчанию его не выдаёт.
- Секрет в факте: когда текст факта содержит секрет, тогда значение маскируется до записи.

#### FR-42: Управление памятью

Администратор SHALL иметь возможность просматривать, редактировать и удалять записи M1–M4.

Код в исходной спеке: `R-MEM-07`.

**Consequences (testable):**
- Удаление ошибочного факта: когда администратор удаляет запись M3 или M4, тогда последующие запуски её не получают.
- Нет прав: когда участник без права пытается удалить запись, тогда отказ в доступе.
- Правка записи: когда администратор исправляет запись M3, тогда следующий запуск получает исправленную версию.

#### FR-43: Срок хранения

Записи M1–M4 MUST становиться недоступными для чтения по истечении срока хранения из профиля памяти. M3 и M4 Memory API SHALL удалять сам; M1 и M2 лежат в таблицах форка: Memory не отдаёт записи старше срока, строки удаляет ICPlan по своему сроку (FR-13, AD-25).

Код в исходной спеке: `R-MEM-08`.

**Consequences (testable):**
- Истёк срок: когда срок хранения записи истёк, тогда запись недоступна для чтения.
- M1 и M2 старше срока: когда сообщение `agent_chat_message` старше срока M1 и итог запуска в `agent_run` старше срока M2 профиля агента, тогда Memory не отдаёт ни сообщение, ни итог в контекст; строки обеих таблиц остаются на месте.
- Срок не истёк: когда запись младше срока, тогда запись доступна.
- M3 закрытой задачи: когда задача закрыта, после закрытия выполнен очередной `POST /retention/run` (CronJob), тогда M3 задачи удалена, M2 остаётся; до этого запуска M3 закрытой задачи не отдаётся в контекст.
- Удаление в журнале: когда `POST /retention/run` удалил записи M3, тогда ответ `{deleted: {m3}}` и запись в журнале Memory API: сколько записей и по какому сроку удалено.
- Сбой очистки: когда `POST /retention/run` завершился ошибкой (БД недоступна), тогда записи остаются, задание CronJob помечено неуспешным и повторяется; неуспешное задание поднимает уведомление эксплуатации.

#### FR-44: Проверки записи в память

Запись в каждый уровень памяти SHALL идти по правилам таблицы «Правила записи по уровням» (`interfaces.md`): в своё время, своим инициатором и после проверок — профиль записи, область видимости, схема и размер, отсутствие секретов, идемпотентность. Запись, не прошедшая проверку, MUST NOT выполняться; причина MUST возвращаться инициатору и попадать в события запуска.

Код в исходной спеке: `R-MEM-15`.

**Consequences (testable):**
- Секрет в M3: когда агент пишет в M3 запись с токеном доступа, тогда запись отклонена, тулу возвращена причина «секрет в записи», событие.
- Уровень не в профиле: когда агент с профилем записи «нет» вызывает запись M3, тогда запись отклонена с причиной «уровень не разрешён профилем».
- Повтор итога запуска: когда Runner повторно отправил итог запуска с тем же `run_id`, тогда в M2 одна запись, дубля нет.
- Слишком большая запись: когда запись M3 больше `m3_max_kb`, тогда запись отклонена с границей в причине.

#### FR-45: Предложения агента по навыкам и плейбуку

Агент MAY предлагать изменение своих навыков и плейбука (M5) как предложение с обоснованием и ссылкой на запуски; предложение MUST NOT менять M5 само. Применять предложение SHALL администратор новой версией настроек агента после прогона регрессионного набора эталонных задач и утверждения человеком; версию SHALL быть возможно откатить. Правило «M5 меняет только администратор» сохраняется в части применения. R&D, AD-27.

Код в исходной спеке: `R-MEM-16`.

**Consequences (testable):**
- Агент предлагает изменение: когда агент по итогам запусков записывает предложение «добавить в навык проверку миграций», тогда предложение сохранено со ссылкой на запуски, определение агента не изменилось, администратор видит предложение в очереди.
- Применение после регрессии: когда администратор принимает предложение, регрессионный набор пройден без ухудшения и человек утвердил, тогда создаётся новая версия настроек (4.4), следующий запуск использует её.
- Регрессия ухудшилась: когда на регрессионном наборе результат хуже текущей версии, тогда версия не создаётся, предложение возвращается с результатом набора.
- Откат: когда администратор откатывает версию, созданную из предложения, тогда действует предыдущая версия настроек, предложение помечено «откатено».

#### FR-46: Записи обучения — источник, исход, TTL, счётчики

Модуль SHALL принимать запись обучения (факт, правило плейбука, навык) только с источником (запуск или задача), исходом, версией и TTL (`learning_ttl_days`), вести счётчики helpful/harmful и дедупликацию, помечать тип записи «справка, не правило» и применять новое правило только после `quarantine_n` подтверждений (ограничения О1, О3, О9, О11, О12 каталога). Запись без источника MUST отклоняться; запись старше TTL без использования MUST NOT отдаваться агенту без проверки актуальности.

Код в исходной спеке: `R-MEM-17`.

**Consequences (testable):**
- Запись без источника: когда в память пытаются записать правило без ссылки на запуск или задачу, тогда запись отклонена, в журнале причина «нет источника».
- Справка не становится правилом: когда запись помечена типом «справка», тогда в контекст агента она попадает в разделе справки, а не в разделе правил.
- Карантин нового правила: когда новое правило подтверждено менее `quarantine_n` раз, тогда правило не применяется к запускам; после `quarantine_n`-го подтверждения становится доступным.
- Просроченная запись: когда запись не использовалась дольше `learning_ttl_days`, тогда перед использованием её актуальность проверяется; не подтверждена — запись помечается устаревшей и не отдаётся.

#### FR-47: Режимы обучения по видам, просмотр, правка и удаление памяти

Модуль SHALL выполнять для каждого вида обучения (`facts`, `playbook`, `skills`, `prompt_opt`) эффективный режим `off`, `suggest` или `apply_gated` (по умолчанию `off` для всех видов), который вычисляет политика уровней control-plane. При режиме `off` модуль MUST NOT создавать новые записи этого вида и MUST NOT удалять накопленные. Пользователь с правом на проект SHALL просматривать, править и удалять записи; удаление действует со следующего запуска. Контракты хранилищ — адаптеры `MemoryStore`, `PlaybookStore`, `SkillRegistry`, `PromptOptimizer` (interfaces.md).

Код в исходной спеке: `R-MEM-18`.

**Consequences (testable):**
- Выключение: когда администратор переводит вид «факты» из `suggest` в `off`, тогда новые записи не создаются в течение 1 минуты, накопленные записи сохранены (потерь 0).
- Удаление записи: когда пользователь удаляет запись памяти в экране 4.4, тогда со следующего запуска запись не отдаётся агенту, удаление видно в журнале изменений.
- Правка записи: когда пользователь правит текст записи, тогда сохраняется новая редакция с автором и временем, прежняя остаётся в журнале.
- Режим по умолчанию: когда у агента не задан режим вида «плейбук», тогда действует `off`: предложений и записей плейбука нет.

#### FR-48: Конфигурация модуля

Модуль SHALL брать свои параметры (8, таблица «Параметры модуля» в `interfaces.md`) с уровней L1 (S2): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-MEM-09`.

**Consequences (testable):**
- Значение по умолчанию: когда `m3_max_kb` (предельный размер записи M3) не задан в конфигурации, тогда применяется значение по умолчанию: 16.
- Выше максимума: когда `m3_max_kb` задан больше 64, тогда значение отклонено, ошибка называет `m3_max_kb` и границы 2–64.
- Ниже минимума: когда `m2_last_runs` задан меньше 0, тогда значение отклонено, ошибка называет `m2_last_runs` и границы 0–10.

#### FR-49: Хранилища данных

Модуль SHALL хранить свои данные только в S4 (Postgres ICPlan, схема `memory`) (`interfaces.md`); данные S1 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-MEM-10`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет состояние задач (M3); факты (M4), тогда запись попадает в S4 (Postgres ICPlan, схема `memory`).
- S4 недоступно: когда S4 (Postgres ICPlan, схема `memory`) не отвечает, тогда чтение — пустой контекст с предупреждением; запись — повтор.
- Доступ вне своих хранилищ: когда код agent-memory обращается к таблицам вне S4, тогда доступа нет: роль БД agent-memory ограничена S4.

#### FR-50: Интерфейсы обмена

Интерфейсы модуля (I11, I2, I22) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-MEM-11`.

**Consequences (testable):**
- Таймаут I11: когда Harness → Memory API (I11) не ответил за 2 с, тогда вызов прерывается; повтор: 2 раза.
- Аутентификация I2: когда собеседник по I2 отклонил учётные данные (bearer API-ключ агента), тогда вызов не повторяется, событие с причиной.
- Повтор I2 без дублей: когда вызов I2 повторён после сбоя, тогда дубля нет: да, по (run_id, seq).

#### FR-51: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-MEM-12`.

**Consequences (testable):**
- БД недоступна: когда бд недоступна, тогда чтение — пустой контекст с предупреждением; запись — повтор.
- Конфликт записи M3: когда конфликт записи m3, тогда последняя версия, прежняя в истории.
- Очистка M3 не прошла: когда очистка M3 не прошла: ошибка `POST /retention/run`, задание CronJob неуспешно, тогда записи остаются; M3 закрытых задач не отдаётся в контекст; уведомление эксплуатации, задание CronJob повторяется.
- Профиль памяти не задан: когда профиль памяти агента не задан, тогда применяются значения по умолчанию из таблицы параметров (`read`, `write`, `scope`).

#### FR-52: Развёртывание

Модуль SHALL разворачиваться так: Memory API — Deployment в `itsaplan-agents`, 1–2 реплики, Service ClusterIP; данные — Postgres через PgBouncer. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-MEM-14`.

**Consequences (testable):**
- Установка: когда выполняется `helm install`: Memory API — Deployment в `itsaplan-agents`, 1–2 реплики, Service ClusterIP; данные — Postgres через PgBouncer, тогда объекты созданы в своём namespace с заданными requests / limits, проверки готовности зелёные.
- Обновление: когда выходит новая версия образа `memory-api` (1–2 реплики), тогда `memory-api` заменяется по одной реплике; работа, начатая на старой версии, доделывается.
- Нехватка ресурсов: когда узлу не хватает ресурсов для пода `memory-api`, тогда под `memory-api` ждёт размещения, событие эксплуатации.

### 4.4 agent-registry

**Description:** Единый версионируемый каталог ресурсов платформы и декларативных определений агентов, из которых агент собирается без написания кода. Обоснование: R&D.

**Functional Requirements:**

#### FR-53: Каталог ресурсов

Registry (ICPlan) SHALL хранить ресурсы типов `model`, `skill`, `tool`, `mcp_server`, `agent` (инструкция, проекты, версия); бюджеты, профили sandbox и памяти, данные guardrails, уровень автономии и политику доступа SHALL хранить Platform module (control-plane).

Код в исходной спеке: `R-REG-01`.

**Consequences (testable):**
- Регистрация ресурса: когда администратор добавляет ресурс любого из типов, тогда ресурс получает идентификатор и версию и становится доступен для ссылок.
- Дубликат: когда добавляется ресурс с существующим идентификатором, тогда добавление отклоняется.
- Неизвестный тип: когда добавляется ресурс неподдерживаемого типа, тогда отказ с перечнем допустимых типов.

#### FR-54: Определение агента

Определение агента SHALL состоять из: модель (алиас), инструкция и формат результата, навыки, тулы и MCP-серверы (ссылки на ресурсы Registry), проекты, версия. Профили памяти и sandbox, данные guardrails и автономия — настройки агента в Platform module (control-plane).

Код в исходной спеке: `R-REG-02`.

**Consequences (testable):**
- Добавление агента без кода: когда администратор сохраняет новое определение агента, тогда агент доступен для запуска по `agent_id` без изменения кода платформы.
- Обязательное поле отсутствует: когда в определении нет модели, тогда сохранение отклоняется с указанием поля.
- Выключение агента: когда агент выключен (`agent.enabled = false`, FR-11), тогда новые запуски не создаются, история сохраняется.

#### FR-55: Версионирование

Каждое изменение ресурса SHALL создавать новую версию; прежние версии MUST оставаться доступными.

Код в исходной спеке: `R-REG-03`.

**Consequences (testable):**
- Запуск на прежней версии: когда задача указывает конкретную версию агента, тогда запуск использует эту версию, даже если есть более новая.
- Новая версия: когда администратор меняет инструкцию, тогда создаётся новая версия, прежние доступны.
- Несуществующая версия: когда задача указывает версию, которой нет, тогда запуск отклоняется с ошибкой версии.

#### FR-56: Источник правды и экспорт

Определения агентов SHALL храниться в БД ICPlan как источнике правды; система SHALL поддерживать экспорт и импорт определений в YAML для ревью и переноса между окружениями.

Код в исходной спеке: `R-REG-04`.

**Consequences (testable):**
- Перенос в prod: когда администратор экспортирует агента из dev и импортирует в prod, тогда в prod создаётся новая версия агента с тем же содержимым.
- Экспорт: когда администратор выгружает агента, тогда получает YAML `agent/v1` без секретов.
- Импорт с другой схемой: когда YAML другой major-версии схемы (`agent/v2` при поддержке `agent/v1`), тогда импорт отклоняется с указанием поддерживаемой версии.
- Импорт с незнакомыми полями: когда YAML той же major-версии содержит поля, которых нет в схеме, тогда импорт выполняется, незнакомые поля перечислены в предупреждении и не сохраняются.

#### FR-57: Валидация связей

Registry MUST отклонять сохранение определения агента со ссылками на несуществующие ресурсы.

Код в исходной спеке: `R-REG-05`.

**Consequences (testable):**
- Битая ссылка: когда определение агента ссылается на несуществующий скилл, тогда сохранение отклоняется с указанием битой ссылки.
- Все ссылки верны: когда определение ссылается на существующие ресурсы, тогда сохранение проходит.
- Удаление используемого ресурса: когда удаляют MCP-сервер, на который ссылается агент, тогда удаление отклоняется со списком агентов.

#### FR-58: Смена модели агента

Смена модели агента SHALL выполняться изменением ссылки на модель в определении, без изменения остальных частей.

Код в исходной спеке: `R-REG-06`.

**Consequences (testable):**
- Замена модели: когда администратор меняет модель агента, тогда новые запуски используют новую модель, активные запуски не затронуты.
- Модель без доступа: когда новая модель не настроена в шлюзе, тогда смена отклоняется.
- Откат модели: когда администратор возвращает прежнюю модель, тогда следующий запуск идёт на прежней модели.
- Шлюз недоступен: когда LiteLLM недоступен в момент сохранения агента со сменой модели, тогда смена модели не сохраняется, администратор видит причину «проверить модель нельзя»; правка без смены модели сохраняется.

#### FR-59: Конфигурация модуля

Модуль SHALL брать свои параметры (7, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L3 (запуск): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Изменение настройки SHALL действовать со следующего запуска; обязательные поля MUST проверяться при сохранении.

Код в исходной спеке: `R-REG-07`.

**Consequences (testable):**
- Значение по умолчанию: когда `agent.tools` (тулы агента из каталога) не задан в настройках, тогда применяется значение по умолчанию: нет.
- Нет обязательного поля: когда настройку сохраняют без `agent.model`, тогда сохранение отклонено, ошибка называет `agent.model`.
- Изменение настройки: когда `agent.model` изменён во время запуска, тогда активный запуск работает со старым значением, новое — со следующего.

#### FR-60: Хранилища данных

Модуль SHALL хранить свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) (`interfaces.md`); данные S2 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-REG-08`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет определения агентов: модель, инструкция, тулы, навыки, MCP-серверы,…, тогда запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`).
- S1 недоступно: когда S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает, тогда определения не читаются — запуски не стартуют.
- Доступ вне своих хранилищ: когда код agent-registry обращается к таблицам вне S1, тогда доступа нет: роль БД agent-registry ограничена S1.

#### FR-61: Интерфейсы обмена

Интерфейсы модуля (I20, I1) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-REG-09`.

**Consequences (testable):**
- Таймаут I1: когда ICPlan → Agent Runner: определение агента в выданном запуске (`/agent-runs/claim`) (I1) не ответил за 10 с, тогда вызов прерывается; повтор: backoff до 60 с.
- Права по I20: когда пользователь без права изменения меняет определения агентов: модель, инструкция, тулы, навыки, MCP-серверы, проекты, версии, тогда API ICPlan отклоняет запрос (403), данные не меняются, событие в журнале.
- Повтор I1 без дублей: когда вызов I1 повторён после сбоя, тогда дубля нет: аренда: выдаётся одному Runner.

#### FR-62: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-REG-10`.

**Consequences (testable):**
- БД ICPlan недоступна: когда бд icplan недоступна, тогда определения не читаются — запуски не стартуют.
- Удалён ресурс, на который ссылаются: когда удалён ресурс, на который ссылаются, тогда удаление отклоняется.
- Импорт с неверной схемой: когда импорт с неверной схемой, тогда импорт отклоняется.

#### FR-63: Развёртывание

Модуль SHALL разворачиваться так: часть ICPlan api (Deployment `api` в `itsaplan-core`). Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-REG-12`.

**Consequences (testable):**
- Установка в составе ICPlan: когда разворачивается релиз ICPlan (часть ICPlan api (Deployment `api` в `itsaplan-core`)) с модулем agent-registry, тогда миграции agent-registry применены до старта `api`, модуль доступен в ICPlan.
- Обновление: когда выходит новая версия форка ICPlan с изменениями agent-registry, тогда миграции agent-registry обратно совместимы, `api` обновляется по одной реплике без простоя.
- Откат: когда версия с изменениями agent-registry не прошла проверки готовности, тогда Helm откатывает ревизию, данные agent-registry сохранены.

#### FR-64: Снимки агента

Registry SHALL создавать снимок агента как неизменяемую версию: конфигурация (`AgentSettings`) + память обучения + плейбук + навыки + версия модели (алиас). Снимок создаётся автоматически перед каждым применением изменения от обучения, вручную и по расписанию `snapshots.schedule`; хранится `snapshots.retention_days` (задаёт человек). Снимок MUST NOT изменяться после создания.

Код в исходной спеке: `R-REG-13`.

**Consequences (testable):**
- Снимок перед применением: когда администратор применяет изменение плейбука (режим `apply_gated`), тогда до применения создан снимок, применённая версия ссылается на него.
- Ручной снимок: когда владелец агента создаёт снимок вручную, тогда снимок появляется в списке с автором и временем; содержит все пять частей.
- Попытка изменить снимок: когда запрос меняет содержимое существующего снимка, тогда отказ, создаётся новая версия, прежний снимок не тронут.
- Срок хранения: когда снимок старше `snapshots.retention_days`, тогда он удаляется, снимок, на который указывает указатель, не удаляется.

#### FR-65: Откат на снимок и автооткат

Registry SHALL откатывать агента на снимок переносом указателя версии за ≤ 5 минут; откат подтверждается прогоном эталонного набора, результат не хуже снимка в пределах шума повторов. При включённом обучении автооткат (О14) SHALL переносить указатель на предыдущий снимок, если метрика эталона после применения хуже снимка сверх шума, и уведомлять человека.

Код в исходной спеке: `R-REG-14`.

**Consequences (testable):**
- Откат владельцем: когда владелец откатывает агента на снимок N, тогда указатель указывает на снимок N, следующий запуск идёт на нём, операция заняла ≤ 5 минут.
- Автооткат: когда после применения метрика эталона хуже снимка сверх шума, тогда указатель возвращён на предыдущий снимок, человек получил уведомление с причиной.
- Восстановимость: когда проверка запрашивает восстановление любого хранимого снимка, тогда все части снимка восстановимы (100% хранимых снимков).

### 4.5 agent-runner

**Description:** Исполняет задачу, назначенную ICPlan конкретному агенту: поднимает изолированную среду, контролирует лимиты запуска, возвращает результат и убирает среду. Не выбирает агента и не планирует задачи. Обоснование: R&D.

**Functional Requirements:**

#### FR-66: Запуск из очереди ICPlan

Runner SHALL забирать запуск из очереди ICPlan по ключу агента и исполнять агента по его актуальной (или указанной в запуске) версии определения.

Код в исходной спеке: `R-RUN-01`.

**Consequences (testable):**
- Успешный запуск: когда в очереди есть запуск агента, обслуживаемого Runner, тогда Runner берёт его, создаёт запись с `run_id` и статусом `queued`.
- Агент выключен или не найден: когда агент выключен (FR-11) или его определение отсутствует, тогда запуск завершается с ошибкой `agent_unavailable`, sandbox не создаётся.
- Указана версия агента: когда в запуске указана версия 3 при последней 5, тогда агент исполняется по версии 3.

#### FR-67: Планирование по слотам

Runner SHALL запускать взятый из очереди запуск, только когда свободны все его слоты: глобальный, агента, модели и задачи; иначе запуск MUST ждать в статусе `queued` в порядке очереди (`fifo` или `priority`).

Код в исходной спеке: `R-RUN-02`.

**Consequences (testable):**
- Занят слот модели: когда у модели `team-default` заняты все слоты, а агент свободен, тогда запуск ждёт в `queued` и стартует при освобождении слота модели.
- Все слоты свободны: когда свободны глобальный слот, слот агента, модели и задачи, тогда запуск стартует сразу.
- Приоритет: когда при `order: priority` в очереди задачи разного приоритета, тогда первым стартует запуск с высшим приоритетом.
- Старение приоритета: когда при `order: priority` запуск низкого приоритета ждёт дольше `scheduling.aging_s`, тогда его приоритет повышается на уровень за каждый такой интервал, запуск не голодает.

#### FR-68: Режим последовательно или параллельно

Режим `scheduling.mode` SHALL задаваться конфигурацией: `sequential` — одновременно не более одного запуска на всю платформу; `parallel` — по лимитам слотов. Агент с `parallel: false` MUST исполняться строго по одному в любом режиме.

Код в исходной спеке: `R-RUN-03`.

**Consequences (testable):**
- Последовательный режим: когда включён `sequential` и в очереди три запуска разных агентов, тогда они выполняются по одному в порядке очереди.
- Параллельный режим: когда включён `parallel`, `global_max: 4`, три запуска разных агентов, тогда все три идут одновременно.
- Агент без параллели: когда агенту задано `parallel: false`, в очереди два его запуска, тогда второй ждёт завершения первого в любом режиме.

#### FR-69: Слоты при ожидании подтверждения

Запуск в статусе `waiting_approval` SHALL освобождать глобальный слот и слот модели, но MUST удерживать слот задачи; после решения пользователя запуск снова ждёт свободных слотов. Источник: US-RUN-04.

Код в исходной спеке: `R-RUN-04`.

**Consequences (testable):**
- Ожидание approve: когда запуск перешёл в `waiting_approval`, тогда глобальный слот и слот модели освобождены, другие запуски могут стартовать.
- Другой запуск по той же задаче: когда запуск задачи ждёт подтверждения, а в очереди второй запуск этой задачи, тогда второй запуск ждёт: слот задачи занят.
- Решение принято при занятых слотах: когда пользователь одобрил действие, а глобальные слоты заняты, тогда запуск ждёт в `queued` и продолжает с того же шага при освобождении слота.

#### FR-70: Один запуск на задачу

Runner MUST NOT запускать второй запуск по задаче, пока активен первый (`per_issue: 1`).

Код в исходной спеке: `R-RUN-05`.

**Consequences (testable):**
- Два агента на одну задачу: когда по задаче уже идёт запуск, а в очереди появился второй, тогда второй ждёт завершения первого.
- Разные задачи: когда два запуска по разным задачам, тогда оба могут идти одновременно.
- Первый упал: когда активный запуск по задаче завершился ошибкой, тогда следующий запуск по задаче стартует.

#### FR-71: Общие слоты для нескольких Runner

Несколько экземпляров Runner SHALL использовать общие слоты, чтобы лимиты соблюдались суммарно.

Код в исходной спеке: `R-RUN-06`.

**Consequences (testable):**
- Два экземпляра: когда работают два Runner и `global_max: 2`, тогда одновременно идут не более двух запусков на оба экземпляра.
- Один Runner упал: когда экземпляр Runner упал с занятыми слотами, тогда слоты освобождаются по истечении аренды.
- Хранилище слотов недоступно: когда таблица слотов недоступна, тогда новые запуски не стартуют (fail-closed), активные продолжаются.

#### FR-72: Статусы запуска

Система SHALL вести статус каждого запуска: `queued`, `starting`, `running`, `waiting_approval`, `succeeded`, `failed`, `gate_failed`, `canceled`, `limit_exceeded` и передавать смену статуса в ICPlan событием (I2); терминальный статус — итогом `/agent-runs/{id}/result`.

Код в исходной спеке: `R-RUN-07`.

**Consequences (testable):**
- Смена статуса: когда запуск перешёл из `queued` в `running`, тогда ICPlan получает событие смены статуса, в задаче виден новый статус.
- Терминальный статус: когда запуск завершился `gate_failed`, тогда итог с причиной отправлен в ICPlan, статус в ICPlan — `failed` с пометкой «не прошёл проверку».
- Runner перезапущен: когда Runner перезапустился с активными запусками, тогда статусы активных запусков восстанавливаются из S3, ICPlan получает актуальный статус без дублей.

#### FR-73: Возврат результата

Система SHALL по завершении запуска вернуть результат агента в формате, объявленном в определении агента.

Код в исходной спеке: `R-RUN-08`.

**Consequences (testable):**
- Успешное завершение: когда агент завершает работу с результатом, тогда статус становится `succeeded`, результат доступен по `run_id`.
- Результат не по формату: когда итог не соответствует формату из определения, тогда запуск завершается `gate_failed` или с пометкой несоответствия.
- Частичный результат: когда запуск остановлен по лимиту, тогда в задачу передаётся частичный итог с пометкой «не завершено».

#### FR-74: Отмена запуска

Система SHALL позволять отменить активный запуск.

Код в исходной спеке: `R-RUN-09`.

**Consequences (testable):**
- Отмена в очереди: когда запуск отменён, пока ждёт слот в `queued`, тогда он снимается с очереди без создания sandbox.
- Отмена: когда ICPlan отменяет запуск, тогда агент останавливается, sandbox уничтожается, статус `canceled`.
- Повторная отмена: когда отмена приходит для уже отменённого запуска, тогда статус не меняется, ошибки нет.

#### FR-75: Очистка среды

Система MUST уничтожать sandbox после любого терминального статуса.

Код в исходной спеке: `R-RUN-10`.

**Consequences (testable):**
- Падение агента: когда запуск завершается со статусом `failed`, тогда sandbox уничтожен, логи и трейсы сохранены в Observability.
- Успешное завершение: когда запуск завершился `succeeded`, тогда sandbox уничтожен, пул долит.
- Ошибка уничтожения: когда контейнер не удалился, тогда Runner повторяет удаление и пишет событие; слот не занимается.

#### FR-76: Манифест рабочего пространства

Runner SHALL собирать для запуска манифест рабочего пространства — список источников с правом (git-репозиторий: адрес, ветка, read / write; папка: префикс в объектном хранилище, read / write) — из политики доступа агента и передавать его в Sandbox и Harness (`RunBundle`). Источник вне политики MUST NOT попадать в манифест. Модель общего пространства между агентами и место политики — открытый вопрос 📌 ОВ-WS-1, ОВ-WS-2 (R&D).

Код в исходной спеке: `R-RUN-17`.

**Consequences (testable):**
- Манифест собран: когда у агента в политике репозиторий (write) и папка задачи (read), тогда манифест содержит оба источника с правами и уходит в Sandbox и `RunBundle`.
- Нет политики: когда у агента нет ни одного разрешённого источника, тогда манифест пустой, запуск идёт без рабочего пространства, событие.
- Политика недоступна: когда Platform module не ответил, тогда запуск не стартует, причина «нет политики доступа».

#### FR-77: Конфигурация модуля

Модуль SHALL брать свои параметры (27, таблица «Параметры модуля» в `interfaces.md`; 14 из них ведут другие спеки — строки «см.») с уровней L0 (S9), L1 (S2), L2 (S1): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Без обязательных параметров L0 модуль MUST NOT стартовать.

Код в исходной спеке: `R-RUN-11`.

**Consequences (testable):**
- Значение по умолчанию: когда `scheduling.aging_s` (интервал повышения приоритета ждущего запуска при…) не задан в конфигурации, тогда применяется значение по умолчанию: 600.
- Выше максимума: когда `scheduling.aging_s` задан больше 3600, тогда значение отклонено, ошибка называет `scheduling.aging_s` и границы 60–3600.
- Граница от другого параметра: когда `concurrency` задан больше, чем `scheduling.global_max`, тогда значение отклонено: `concurrency` не может быть больше `scheduling.global_max`.

#### FR-78: Хранилища данных

Модуль SHALL хранить свои данные только в S3 (Postgres ICPlan, схема `platform`), S5 (Postgres ICPlan, схема `harness_ckpt`) (`interfaces.md`); данные S2, S9 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-RUN-12`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет события запусков, слоты планировщика, тогда запись попадает в S3 (Postgres ICPlan, схема `platform`).
- S3 недоступно: когда S3 (Postgres ICPlan, схема `platform`) не отвечает, тогда новые запуски не стартуют; события активных буферизуются в памяти Runner.
- Доступ вне своих хранилищ: когда код agent-runner обращается к таблицам вне S3, S5, тогда доступа нет: роль БД agent-runner ограничена S3, S5.

#### FR-79: Интерфейсы обмена

Интерфейсы модуля (I1, I2, I3, I4, I5, I6, I7, I9, I10, I18, I19, I22, I23) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-RUN-13`.

**Consequences (testable):**
- Таймаут I1: когда ICPlan Run Queue → Agent Runner (I1) не ответил за 10 с, тогда вызов прерывается; повтор: backoff до 60 с.
- Аутентификация I2: когда собеседник по I2 отклонил учётные данные (bearer API-ключ агента), тогда вызов не повторяется, событие с причиной.
- Неидемпотентный вызов I6: когда вызов I6 (Agent Runner → Docker Engine API) прервался сбоем сети, тогда автоматического повтора нет, решение принимает вызывающий.
- MCP-прокси запуска: когда Harness вызывает через Runner тул MCP-сервера вне allowlist манифеста запуска, тогда Runner отклоняет вызов без обращения к серверу, решение G2 с причиной — в событиях запуска.

#### FR-80: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-RUN-14`.

**Consequences (testable):**
- ICPlan недоступен: когда icplan недоступен, тогда опрос с backoff, активные запуски продолжаются, события буферизуются.
- Platform module недоступен: когда platform module недоступен, тогда новые запуски не стартуют (нет настроек).
- Docker / пул недоступен: когда docker / пул недоступен, тогда запуск остаётся в `queued`.
- Runner упал: когда runner упал, тогда запуски возвращаются в очередь, слоты освобождаются.
- MCP-сервер недоступен: когда MCP-сервер не ответил на вызов тула через MCP-прокси (I9), тогда агент получает ошибку тула, цикл продолжается; чтение повторяется 2 раза, запись — нет.
- Шаг подготовки упал или превысил `setup.timeout_s`: когда скрипт `setup.script` вернул ненулевой код выхода или шаг подготовки не уложился в `setup.timeout_s`, тогда запуск `failed` с причиной «подготовка среды»; после исправления скрипта или реестра запуск можно повторить.
- Нет настроек агента / ключа: когда Platform module вернул пустой ответ (I4) — нет настроек агента или ключа, тогда запуск завершается статусом `agent_unavailable`, администратор заполняет настройки.

#### FR-81: Развёртывание

Модуль SHALL разворачиваться так: Deployment `agent-runner` в `itsaplan-agents`, 1 реплика (MVP), 2 — с общими слотами; requests 0.1 CPU / 128 МиБ, limits 0.5 / 512 МиБ; без ingress. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-RUN-16`.

**Consequences (testable):**
- Установка: когда выполняется `helm install`: Deployment `agent-runner` в `itsaplan-agents`, 1 реплика (MVP), 2 — с общими слотами; requests 0.1 CPU / 128 МиБ, limits 0.5 / 512 МиБ; без ingress, тогда объекты созданы в своём namespace с заданными requests / limits, проверки готовности зелёные.
- Обновление: когда выходит новая версия образа `agent-runner` (1 реплика), тогда `agent-runner` заменяется по одной реплике; работа, начатая на старой версии, доделывается.
- Нехватка ресурсов: когда узлу не хватает ресурсов для пода `agent-runner`, тогда под `agent-runner` ждёт размещения, событие эксплуатации.

### 4.6 agent-sandbox

**Description:** Изолированная среда исполнения, создаваемая на каждый запуск агента, чтобы запуски не влияли друг на друга и на хост. Обоснование: R&D.

**Functional Requirements:**

#### FR-82: Среда на каждый запуск

Система SHALL выделять отдельный sandbox на каждый запуск и MUST NOT переиспользовать его между запусками.

Код в исходной спеке: `R-SBX-01`.

**Consequences (testable):**
- Два параллельных запуска: когда один агент запущен дважды параллельно, тогда у запусков разные sandbox и они не видят файлы друг друга.
- Последовательные запуски одного агента: когда агент запущен дважды подряд, тогда второй запуск получает новый контейнер без файлов первого.
- Повторное использование запрещено: когда контейнер вернули после запуска, тогда он уничтожается, а не возвращается в пул.

#### FR-83: Тёплый пул

Система SHALL держать по каждому sandbox-профилю заранее запущенные sandbox (размер пула — параметр профиля); запуск SHALL забирать готовый sandbox из пула, а после запуска sandbox MUST уничтожаться, а пул — доливаться.

Код в исходной спеке: `R-SBX-02`.

**Consequences (testable):**
- Быстрый старт: когда в пуле профиля есть свободный sandbox, тогда запуск начинается без создания контейнера, после завершения контейнер уничтожен, в пуле снова N свободных.
- Пул пуст: когда свободных sandbox в пуле нет, тогда sandbox создаётся заново, запуск ждёт его старта.
- Изменён профиль: когда в профиле изменён образ, тогда пул пересоздаёт контейнеры с новым образом.

#### FR-84: Эфемерный workspace

Рабочие файлы запуска SHALL лежать в `/workspace` внутри sandbox и MUST уничтожаться вместе с ним; результаты SHALL сохраняться вне sandbox: код — веткой и PR в целевой репозиторий, документы и артефакты — в задачу ICPlan, состояние задачи и лог — в БД.

Код в исходной спеке: `R-SBX-03`.

**Consequences (testable):**
- После запуска: когда запуск завершился, тогда `/workspace` удалён, код в ветке `agent/<KEY>`, артефакты во вложениях задачи.
- Агент создал артефакт: когда агент сохранил файл-результат, тогда файл загружен во вложения задачи до уничтожения контейнера.
- Переполнен диск: когда workspace превысил лимит диска, тогда запись отклоняется, запуск получает ошибку.

#### FR-85: Доступ к репозиториям

Sandbox SHALL получать доступ только к репозиториям из allowlist агента с указанным уровнем (read или write); токен MUST быть короткоживущим, выдаваться на запуск и подставляться прокси или credential helper, а не через env. Запись в защищённые ветки MUST быть запрещена.

Код в исходной спеке: `R-SBX-04`.

**Consequences (testable):**
- Репозиторий вне allowlist: когда агент пытается клонировать репозиторий не из allowlist, тогда доступ отклонён.
- Push в main: когда агент пытается сделать push в защищённую ветку, тогда push отклонён, разрешена только ветка с префиксом агента.
- Разрешённый репозиторий: когда агент клонирует репозиторий из allowlist, тогда клон в `/workspace` проходит с короткоживущим токеном.

#### FR-86: Профиль sandbox

Параметры sandbox (образ, runtime, CPU, RAM, диск, сетевые правила) SHALL задаваться sandbox-профилем агента из настроек Platform module (`sandbox_profile`, L1).

Код в исходной спеке: `R-SBX-05`.

**Consequences (testable):**
- Тяжёлый агент: когда агент ссылается на профиль с увеличенной RAM, тогда его sandbox создаётся с этой RAM.
- Превышение памяти: когда процесс превысил лимит RAM, тогда контейнер останавливается, запуск получает `failed` с причиной.
- Профиль не найден: когда агент ссылается на несуществующий профиль, тогда запуск отклоняется до создания контейнера.
- Runtime gVisor: когда профиль задаёт `runtime: runsc`, а на узле нет runsc, тогда запуск отклоняется до создания контейнера с причиной «runtime недоступен».

#### FR-87: Сетевая изоляция

Sandbox MUST разрешать исходящие соединения только к Agent Runner (I7, I12, I9 — MCP через прокси Runner), LLM Gateway (I8), OPA (I10), Memory API (I11) и доменам из allowlist профиля — внешние только через egress-прокси (I17). Реестры пакетов MUST быть доступны только шагу подготовки (сеть `sbx-setup`, AD-19).

Код в исходной спеке: `R-SBX-06`.

**Consequences (testable):**
- Запрещённый домен: когда агент обращается к домену вне allowlist, тогда соединение блокируется и событие фиксируется.
- Разрешённый хост: когда агент обращается к LiteLLM, тогда соединение проходит через egress-прокси.
- Прокси недоступен: когда egress-прокси не отвечает, тогда исходящие соединения запрещены (fail-closed).
- Реестр пакетов из среды агента: когда агент из своей среды обращается к `pypi.org`, тогда соединение блокируется; зависимости ставит шаг подготовки.

#### FR-88: Секреты

Секреты MUST NOT передаваться в sandbox в открытом виде; доступ к внешним системам SHALL идти через прокси с подстановкой учётных данных: внешние хосты — egress-прокси, MCP-серверы — MCP-прокси Runner (AD-19).

Код в исходной спеке: `R-SBX-07`.

**Consequences (testable):**
- Вызов тула с ключом: когда тул обращается к внешнему API, тогда ключ подставляется прокси, агент его не видит.
- Секрета нет в env: когда агент читает переменные окружения, тогда значений секретов там нет.
- Секрет в выводе: когда агент пытается вывести заголовок авторизации, тогда прокси не возвращает подставленный секрет агенту.
- Ключ MCP-сервера: когда агент вызывает тул MCP-сервера, тогда учётные данные сервера подставляет MCP-прокси Runner, в sandbox их нет.

#### FR-89: Подключение рабочего пространства по манифесту

Sandbox SHALL подключать источники манифеста в `/workspace/<имя>`: git — клон с короткоживущим токеном и веткой агента; папка — копия из объектного хранилища при старте, своя подпапка шага выгружается обратно в конце запуска. Право read MUST запрещать запись и выгрузку; источник вне манифеста MUST быть недоступен. Модель — AD-18, зависимости — шаг подготовки AD-19 (R&D).

Код в исходной спеке: `R-SBX-14`.

**Consequences (testable):**
- Git и папка: когда в манифесте репозиторий (write) и папка задачи (read), тогда репозиторий склонирован в `/workspace/repo`, папка скопирована в `/workspace/task`, запись — только в репозиторий.
- Выгрузка папки: когда у агента право write на свою подпапку шага, тогда в конце запуска подпапка выгружена в объектное хранилище новой версией.
- Нет права записи: когда агент пишет в папку с правом read, тогда запись отклонена, выгрузки нет.
- Шаг подготовки: когда у проекта задан `setup.script`, а кэша для хеша lock-файлов нет, тогда Runner выполняет скрипт в контейнере подготовки с доступом к `setup.registries`; результат подключён в `/workspace/.deps` до старта агента.
- Кэш подготовки: когда lock-файлы не менялись и кэш моложе `setup.cache_ttl_h`, тогда шаг подготовки пропускается, подключается кэш.

#### FR-90: Конфигурация модуля

Модуль SHALL брать свои параметры (7, таблица «Параметры модуля» в `interfaces.md`) с уровней L1 (S2), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-SBX-08`.

**Consequences (testable):**
- Значение по умолчанию: когда `workspace.sources` (источники рабочего пространства запуска: git,…) не задан в конфигурации, тогда применяется значение по умолчанию: нет.
- Граница от другого параметра: когда `pool.size` задан больше, чем `scheduling.global_max`, тогда значение отклонено: `pool.size` не может быть больше `scheduling.global_max`.
- Недопустимое значение: когда `resources` задан вне допустимых значений (0,25 CPU, 256 МБ, 1 ГБ … 4 CPU, 8 ГБ, 20 ГБ), тогда значение отклонено, ошибка называет `resources` и допустимые значения.

#### FR-91: Хранилища данных

Sandbox SHALL выделять каждому запуску свой диск S10 (`/workspace`) по профилю и MUST уничтожать его вместе со средой; общих томов между запусками MUST NOT быть. Секреты MUST NOT записываться на диск среды.

Код в исходной спеке: `R-SBX-09`.

**Consequences (testable):**
- Выделение диска: когда Runner создаёт среду запуска по профилю `light`, тогда у среды свой `/workspace` размером по профилю, чужих томов нет.
- S10 переполнен: когда `/workspace` превысил лимит диска профиля sandbox, тогда запись отклоняется, агент получает ошибку тула, запуск продолжается или завершается `limit`.
- Уничтожение: когда запуск завершён, тогда диск `/workspace` удалён вместе со средой, данные не переходят в следующий запуск.

#### FR-92: Интерфейсы обмена

Интерфейсы модуля (I6, I7, I17, I18) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-SBX-10`.

**Consequences (testable):**
- Таймаут I6: когда Agent Runner → Docker Engine API (I6) не ответил за 30 с, тогда вызов прерывается; повтор: 1 раз.
- Аутентификация I7: когда собеседник по I7 отклонил учётные данные (одноразовый токен запуска), тогда вызов не повторяется, событие с причиной.
- Неидемпотентный вызов I6: когда вызов I6 (Agent Runner → Docker Engine API) прервался сбоем сети, тогда автоматического повтора нет, решение принимает вызывающий.

#### FR-93: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-SBX-11`.

**Consequences (testable):**
- Нет ресурсов хоста: когда нет ресурсов хоста, тогда запуск ждёт в `queued`.
- Образ недоступен: когда образ недоступен, тогда профиль помечен недоступным, запуски отклоняются.
- Egress-прокси упал: когда egress-прокси упал, тогда исходящий трафик запрещён (fail-closed).
- Переполнен диск workspace: когда переполнен диск workspace, тогда запись отклоняется, агент получает ошибку.
- Реестр пакетов недоступен на шаге подготовки: когда на шаге подготовки реестр пакетов недоступен и установка завершается ошибкой, тогда шаг подготовки завершается ошибкой, запуск `failed` с причиной; при наличии кэша используется кэш.
- Объектное хранилище (RustFS) недоступно при подключении или выгрузке папки: когда S3 API (I19) не отвечает при подключении папки или при её выгрузке, тогда при подключении запуск стартует с ошибкой «нет рабочего пространства»; при выгрузке — повтор 3 раза, затем итог с пометкой «артефакты не сохранены».

#### FR-94: Развёртывание

Модуль SHALL разворачиваться так: этапы 1–3 — Docker на узле; этап 4 — Pod на запуск в `itsaplan-agents`, NetworkPolicy только к egress-прокси; egress-прокси — Deployment 1 реплика. Контейнер среды создаёт Runner на каждый запуск, образ закреплён по digest; ресурсы MUST задаваться профилем sandbox.

Код в исходной спеке: `R-SBX-13`.

**Consequences (testable):**
- Новый образ среды: когда опубликован новый образ среды (`HARNESS_IMAGE`), тогда пул пересоздаёт тёплые контейнеры, новые запуски идут на новом образе, активные доделываются.
- Egress-прокси обновляется: когда выходит новая версия `egress-proxy`, тогда прокси заменяется без разрыва активных соединений больше чем на время переподключения; без прокси исходящий трафик запрещён.
- Нехватка ресурсов: когда узлу не хватает ресурсов для контейнера по профилю, тогда запуск ждёт в `queued`, тёплый пул не доливается до освобождения ресурсов.

### 4.7 control-plane

**Description:** Platform module — модуль ICPlan для настроек агентов, которых нет в ICPlan: бюджеты, профили sandbox и памяти, данные guardrails, параметры планирования, версии определений. UI — экраны ICPlan. Обоснование: R&D.

**Functional Requirements:**

#### FR-95: Настройки агента

Модуль SHALL хранить для агента параметры L1 из `interfaces.md`: `budget.*`, `limits.*`, `rate_limit`, `sandbox_profile`, `memory_profile.*`, `guardrails.*`, `autonomy_level` (AD-18), `concurrency`, `repos`. Алиас модели хранит Registry (`ai_agent.model`, AD-23). Значение выше потолка L0 MUST отклоняться при сохранении с ошибкой, называющей поле и потолок (FR-105); если потолок снизили после сохранения, при запуске SHALL применяться потолок.

Код в исходной спеке: `R-CP-01`.

**Consequences (testable):**
- Сохранение настроек: когда администратор задаёт агенту бюджет 5 $ в сутки и профиль sandbox `light`, тогда настройки сохранены и видны в карточке агента в ICPlan.
- Недопустимое значение: когда администратор задаёт отрицательный бюджет или несуществующий профиль, тогда сохранение отклоняется с указанием поля и причины.
- Уровень автономии: когда администратор задаёт агенту `autonomy_level` R1, тогда уровень сохранён и со следующего запуска действует политика подтверждений R1.
- Выше потолка платформы: когда администратор задаёт `concurrency` больше потолка L0 `scheduling.global_max`, тогда сохранение отклоняется, ошибка называет `concurrency` и потолок.
- Потолок снижен после сохранения: когда у агента сохранён `concurrency` 4, потом потолок L0 `scheduling.global_max` снизили до 2, тогда запуски агента идут не больше чем в 2 потока, в карточке видно, что действует потолок.
- Сброс к умолчаниям: когда администратор сбрасывает настройку, тогда используется значение по умолчанию из таблицы конфигурации.
- Удаление используемого профиля: когда владелец экземпляра удаляет профиль sandbox или памяти, который указан в настройках агентов, тогда удаление отклоняется с кодом 409, в ответе перечислены агенты с этим профилем.

#### FR-96: Хранение в БД ICPlan

Настройки MUST храниться в БД ICPlan в отдельной схеме модуля; доступ исполнителей SHALL идти через API модуля, а не напрямую к таблицам.

Код в исходной спеке: `R-CP-02`.

**Consequences (testable):**
- Чтение Runner: когда Agent Runner запрашивает настройки агента перед запуском, тогда получает их через API модуля.
- Прямой доступ запрещён: когда сервис пытается читать таблицы модуля напрямую, тогда доступа нет, только через API.
- Обновление ICPlan: когда форк обновлён из upstream, тогда схема модуля не затрагивается миграциями ICPlan.

#### FR-97: Применение к следующему запуску

Изменение настроек SHALL применяться к следующим запускам и MUST NOT менять активные запуски, кроме бюджетов и аварийной остановки: они SHALL действовать сразу (лимит ключа LiteLLM, kill switch).

Код в исходной спеке: `R-CP-03`.

**Consequences (testable):**
- Смена профиля во время запуска: когда администратор меняет профиль sandbox, пока идёт запуск, тогда активный запуск работает по прежнему профилю, следующий — по новому.
- Уменьшение бюджета во время запуска: когда администратор уменьшает бюджет агента ниже уже потраченного, тогда LiteLLM применяет новый лимит сразу: запуск останавливается с причиной «бюджет», событие.
- Запуск в очереди: когда настройки изменены, пока запуск ждёт в `queued`, тогда запуск стартует с новыми настройками.

#### FR-98: Версии настроек агента

Каждое изменение настроек агента в Platform module SHALL сохраняться версией с автором и временем; администратор SHALL откатывать настройки к прежней версии. Версии определения агента ведёт Registry (FR-55).

Код в исходной спеке: `R-CP-04`.

**Consequences (testable):**
- История изменений: когда администратор открывает историю настроек агента, тогда видны версии: кто, когда, что изменено.
- Откат: когда администратор откатывает настройки на версию 3, тогда создаётся новая версия с содержимым версии 3, действует со следующего запуска.
- Нет прав на откат: когда участник без права управления агентами пытается откатить, тогда отказ в доступе.

#### FR-99: Экспорт и импорт YAML

Модуль SHALL экспортировать определение агента с настройками в YAML `agent/v1` и импортировать его, проверяя схему и ссылки.

Код в исходной спеке: `R-CP-05`.

**Consequences (testable):**
- Перенос в prod: когда администратор импортирует YAML, выгруженный из dev, тогда в prod создаётся новая версия агента с тем же содержимым.
- Битая ссылка при импорте: когда YAML ссылается на несуществующий MCP-сервер, тогда импорт отклоняется с указанием ссылки.
- Секреты не экспортируются: когда администратор экспортирует агента, тогда в YAML только ссылки на секреты, без значений.

#### FR-100: Раздача настроек исполнителям

Модуль SHALL передавать алиасы и бюджеты в LiteLLM, а данные правил — в OPA; рассинхронизация MUST обнаруживаться и показываться администратору.

Код в исходной спеке: `R-CP-06`.

**Consequences (testable):**
- Новое правило: когда администратор добавляет тул в список с подтверждением, тогда следующий вызов этого тула агентом ждёт approve (данные в OPA обновлены).
- LiteLLM недоступен: когда при сохранении бюджета LiteLLM не отвечает, тогда изменение помечается «не применено» и повторяется.
- Рассинхронизация: когда бюджет в модуле и в LiteLLM различается, тогда администратор видит предупреждение.

#### FR-101: Права на настройки

Изменять настройки SHALL только роли с правом управления агентами; остальные MUST получать отказ.

Код в исходной спеке: `R-CP-07`.

**Consequences (testable):**
- Нет прав: когда участник без права пытается изменить бюджет агента, тогда запрос отклоняется с ошибкой доступа.
- Есть права: когда администратор меняет бюджет, тогда изменение сохраняется и попадает в историю.
- Только чтение: когда участник с правом чтения открывает настройки, тогда видит, но не может менять.

#### FR-102: Руководство проекта для агентов

Администратор SHALL задавать руководство проекта — общие правила для всех агентов проекта (репозитории по умолчанию, стиль, ограничения). Руководство SHALL храниться в Platform module (S2), передаваться в `RunBundle` и действовать со следующего запуска; длина MUST быть не больше `prompt.guidance_max_chars`.

Код в исходной спеке: `R-CP-14`.

**Consequences (testable):**
- Руководство задано: когда администратор сохранил руководство проекта, тогда новые запуски всех агентов проекта получают его слоем после системного промпта.
- Слишком длинное: когда руководство длиннее `prompt.guidance_max_chars`, тогда сохранение отклонено с границей.
- Нет руководства: когда руководство не задано, тогда слой пропускается, запуск идёт без него.

#### FR-103: Настройки обучения агента и политика уровней

Модуль SHALL хранить в настройках агента блоки `learning` (режим по видам `facts`, `playbook`, `skills`, `prompt_opt`: `off`, `suggest`, `apply_gated`; по умолчанию `off`), `snapshots` (расписание, срок хранения), `toolsmith` (вкл/выкл, по умолчанию выкл) и `guardrails` (включение и параметры О1–О15). Эффективный режим вида MUST вычисляться как самое строгое из значений агента, проекта, команды и политики администратора; режим выше `suggest` MUST быть недоступен, пока не включены О4, О12, О14. Изменения применяются без релиза; выключение не удаляет накопленное.

Код в исходной спеке: `R-CP-15`.

**Consequences (testable):**
- Строже побеждает: когда у агента `apply_gated`, у проекта `suggest`, политика администратора не ограничивает, тогда эффективный режим вида `suggest`.
- Запрет администратора: когда администратор запрещает `apply_gated` для команды, тогда проект команды не может включить режим выше `suggest`; результат верен для всех сочетаний уровней.
- Режим выше «предлагать» без ограничений: когда сохраняется `apply_gated` при выключенном О14, тогда сохранение отклонено, ошибка называет О14.
- Смена режима без деплоя: когда владелец проекта меняет режим «факты» с `off` на `suggest`, тогда режим действует со следующего запуска, за ≤ 1 минуты, релиз не нужен.

#### FR-104: Экраны обучения, снимков, инструментальщика и ограничений

Platform module SHALL показывать в экранах AD-24 (карточка агента, Проект → ИИ-команда): режимы обучения по видам, снимки и откат, переключатель инструментальщика, набор ограничений О1–О15, просмотр и правка памяти, журнал изменений. Менять эти настройки MAY администратор и владелец проекта в пределах своих прав (`ai_agents`); значение выше потолка администратора MUST отклоняться.

Код в исходной спеке: `R-CP-16`.

**Consequences (testable):**
- Экран обучения: когда владелец проекта открывает «Платформа» агента, тогда видны режимы по видам с эффективным значением и уровнем, определившим его.
- Откат из экрана: когда владелец выбирает снимок N и подтверждает откат, тогда выполняется FR-65, в журнале запись об откате.
- Без права: когда пользователь без права `ai_agents` открывает экран, тогда настройки обучения только для чтения.

#### FR-105: Конфигурация модуля

Модуль SHALL брать свои параметры (26, таблица «Параметры модуля» в `interfaces.md`) с уровней L1 (S2), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Изменение настройки SHALL действовать со следующего запуска; обязательные поля MUST проверяться при сохранении.

Код в исходной спеке: `R-CP-08`.

**Consequences (testable):**
- Значение по умолчанию: когда `prompt.guidance` (руководство проекта для всех агентов проекта) не задан в настройках, тогда применяется значение по умолчанию: нет.
- Выше максимума: когда `prompt.guidance_max_chars` задан больше 16000, тогда значение отклонено, ошибка называет `prompt.guidance_max_chars` и границы 0–16000.
- Граница от другого параметра: когда `prompt.guidance` задан больше, чем `prompt.guidance_max_chars`, тогда значение отклонено: `prompt.guidance` не может быть больше `prompt.guidance_max_chars`.

#### FR-106: Хранилища данных

Модуль SHALL хранить свои данные только в S2 (Postgres ICPlan, схема `platform`) (`interfaces.md`); данные S6, S9 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-CP-09`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет настройки агентов, версии, профили sandbox и памяти, данные…, тогда запись попадает в S2 (Postgres ICPlan, схема `platform`).
- S2 недоступно: когда S2 (Postgres ICPlan, схема `platform`) не отвечает, тогда сохранение настроек отклоняется с причиной; Runner не стартует новые запуски (нет настроек).
- Доступ вне своих хранилищ: когда код control-plane обращается к таблицам вне S2, тогда доступа нет: роль БД control-plane ограничена S2.

#### FR-107: Интерфейсы обмена

Интерфейсы модуля (I4, I15, I16, I20, I22) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-CP-10`.

**Consequences (testable):**
- Таймаут I4: когда Agent Runner → Platform module API (I4) не ответил за 2 с, тогда вызов прерывается; повтор: 3 раза.
- Аутентификация I15: когда собеседник по I15 отклонил учётные данные (master key (Secret)), тогда вызов не повторяется, событие с причиной.
- Повтор I15 без дублей: когда вызов I15 повторён после сбоя, тогда дубля нет: да, по алиасу ключа.

#### FR-108: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-CP-11`.

**Consequences (testable):**
- LiteLLM admin API недоступен: когда litellm admin api недоступен, тогда изменение помечено «не применено», повтор.
- OPA не забрал bundle: когда opa не забрал bundle, тогда решения по старым данным, предупреждение администратору.
- Рассинхронизация настроек: когда рассинхронизация настроек, тогда предупреждение, новые запуски используют S2.

#### FR-109: Развёртывание

Модуль SHALL разворачиваться так: модуль ICPlan api (`itsaplan-core`); OPA забирает bundle по HTTP раз в 30 с. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-CP-13`.

**Consequences (testable):**
- Установка в составе ICPlan: когда разворачивается релиз ICPlan (модуль ICPlan api (`itsaplan-core`); OPA забирает bundle по HTTP раз в 30 с) с модулем control-plane, тогда миграции control-plane применены до старта `api`, модуль доступен в ICPlan.
- Обновление: когда выходит новая версия форка ICPlan с изменениями control-plane, тогда миграции control-plane обратно совместимы, `api` обновляется по одной реплике без простоя.
- Откат: когда версия с изменениями control-plane не прошла проверки готовности, тогда Helm откатывает ревизию, данные control-plane сохранены.

### 4.8 guardrails

**Description:** Единая настраиваемая политика безопасности и ограничений агентов, хранимая в Registry и применяемая в четырёх точках: G1 Admission, G2 Action, G3 Isolation, G4 LLM. Обоснование: R&D.

**Functional Requirements:**

#### FR-110: Единый источник правил

Логика правил SHALL храниться в git (Rego, S8), данные правил агента (allowlist, подтверждения, лимиты) — в Platform module (S2); OPA SHALL получать их бандлом (I16). Каждое правило MUST иметь точку применения (G1–G4).

Код в исходной спеке: `R-GRD-01`.

**Consequences (testable):**
- Новое правило: когда администратор добавляет правило с точкой G2 агенту, тогда правило применяется в следующих запусках этого агента.
- Правило без точки: когда правило не указывает точку G1–G4, тогда сохранение отклоняется.
- Удаление правила: когда администратор удаляет правило, тогда следующие запуски проверяются без него.

#### FR-111: G1 Admission

До создания sandbox система MUST проверять: допуск агента к задаче/инициатору, бюджет токенов/$, лимит параллельных запусков, kill switch.

Код в исходной спеке: `R-GRD-02`.

**Consequences (testable):**
- Исчерпан бюджет: когда бюджет агента исчерпан, тогда запуск отклоняется со статусом `limit_exceeded`, sandbox не создаётся.
- Допуск пройден: когда у агента есть бюджет и доступ к задаче, тогда sandbox создаётся, запуск стартует.
- Kill switch агента: когда для агента включён kill switch, тогда запуск отклоняется до создания sandbox.

#### FR-112: G2 Action

Harness MUST проверять каждый вызов тула (allowlist, валидация аргументов), доступ к памяти и итоговый результат; для действий, помеченных опасными, SHALL требоваться подтверждение человека. Для вызовов MCP проверку MUST повторять MCP-прокси Runner вне sandbox (AD-19).

Код в исходной спеке: `R-GRD-03`.

**Consequences (testable):**
- Опасное действие: когда агент вызывает тул, помеченный как требующий подтверждения, тогда вызов приостанавливается до подтверждения человеком.
- Injection в результате тула: когда результат тула содержит признаки prompt injection, тогда результат помечается или фильтруется до передачи в LLM.
- Разрешённый тул: когда агент вызывает тул из allowlist без пометки опасности, тогда тул выполняется без паузы.
- Подтверждение до конца запуска: когда пользователь подтвердил вызов с областью «до конца запуска» (`scope: run`), тогда повторные вызовы этого тула в запуске идут без паузы; с областью `once` — пауза при каждом вызове.

#### FR-113: G3 Isolation

Sandbox MUST применять сетевой allowlist, ограничение записи ФС рабочей директорией, лимиты ресурсов и запрет привилегированного режима.

Код в исходной спеке: `R-GRD-04`.

**Consequences (testable):**
- Запись вне workspace: когда агент пытается записать файл вне рабочей директории, тогда запись запрещена.
- Запись в workspace: когда агент пишет файл в `/workspace`, тогда запись разрешена.
- G3 выключен: когда в конфиге `g3.enabled: false`, тогда профиль ограничений не применяется, в логе старта — предупреждение.

#### FR-114: G4 LLM

LLM Gateway MUST применять allowlist моделей агента, лимиты токенов/$, маскирование PII и секретов во входе, детект jailbreak/injection и модерацию ответа.

Код в исходной спеке: `R-GRD-05`.

**Consequences (testable):**
- Секрет в промпте: когда промпт содержит строку, похожую на ключ API, тогда строка маскируется до отправки провайдеру.
- Чистый промпт: когда в промпте нет секретов и PII, тогда запрос уходит без изменений.
- Модерация ответа: когда ответ модели нарушает политику модерации, тогда ответ блокируется, агент получает отказ.

#### FR-115: Включение и выключение точек

Каждая точка G1–G4 SHALL включаться и выключаться независимо конфигурацией деплоя (YAML). Выключенная точка MUST NOT блокировать работу платформы; факт выключения SHALL логироваться при старте.

Код в исходной спеке: `R-GRD-06`.

**Consequences (testable):**
- G2 выключен: когда в конфиге деплоя `guardrails.g2.enabled: false`, тогда Harness не вызывает проверку G2, запуски работают, в логе старта — «G2 disabled».
- Все точки включены: когда все `gN.enabled: true`, тогда проверки идут во всех точках.
- Неверный конфиг: когда в конфиге неизвестная точка `g5`, тогда сервис не стартует с понятной ошибкой.

#### FR-116: Движок решений для G1 и G2

Решения G1 и G2 SHALL приниматься движком политик (OPA): логика правил (Rego) хранится в git, данные правил (allowlist, лимиты агента) — в БД ICPlan. При недоступности движка включённая точка MUST отказывать (fail-closed), если в конфиге не задано иное.

Код в исходной спеке: `R-GRD-07`.

**Consequences (testable):**
- Движок недоступен: когда G2 включён, а OPA не отвечает, тогда вызов тула отклоняется с причиной `policy_unavailable`.
- Режим allow при сбое: когда задано `on_engine_error: allow`, OPA недоступен, тогда вызов разрешается, решение помечается «без проверки».
- Задержка решения: когда OPA отвечает медленнее таймаута, тогда считается недоступным, действует `on_engine_error`.

#### FR-117: Уровень автономии агента

Агенту SHALL назначаться уровень автономии R0–R5, определяющий политику подтверждений: R0 — только предлагает; R1 — подтверждение каждого действия с записью; R2 — подтверждение опасных действий; R3 — подтверждение только необратимых; R4 — без подтверждений, с аудитом; R5 — полностью сам. Необратимые действия в продуктивной среде MUST требовать подтверждения на любом уровне.

Код в исходной спеке: `R-GRD-08`.

**Consequences (testable):**
- Агент R2: когда агент уровня R2 вызывает тул, помеченный опасным, тогда вызов ждёт подтверждения человека.
- Релиз в prod: когда агент уровня R5 пытается выполнить релиз в продуктивную среду, тогда действие всё равно ждёт подтверждения.
- Агент R4: когда агент уровня R4 выполняет опасное, но обратимое действие, тогда действие выполняется без паузы и пишется в аудит.

#### FR-118: Защита от зацикливания

Harness MUST останавливать запуск со статусом `limit_exceeded` и причиной `loop_detected`, если агент повторяет один и тот же вызов тула с теми же аргументами и тем же результатом больше N раз подряд (по умолчанию 3) или K шагов подряд не меняет состояние задачи (по умолчанию 8). Детерминированная проверка, без LLM.

Код в исходной спеке: `R-GRD-09`.

**Consequences (testable):**
- Повтор вызова: когда агент третий раз подряд вызывает `get_issue` с теми же аргументами, тогда запуск останавливается: статус `limit_exceeded`, причина `loop_detected`, частичный итог сохраняется, в чате запуска — причина.
- Разные аргументы: когда агент трижды вызывает тул с разными аргументами, тогда это не считается зацикливанием.
- Нет прогресса: когда 8 шагов подряд состояние задачи не меняется, тогда запуск останавливается: статус `limit_exceeded`, причина `loop_detected`.
- Опрос: когда агент трижды вызывает тул статуса CI с теми же аргументами, а результат меняется, тогда это не зацикливание, запуск продолжается.

#### FR-119: Лимит шагов и времени

Каждый запуск MUST иметь лимит шагов цикла, общего времени и времени простоя (нет событий); при превышении запуск SHALL завершаться со статусом `limit_exceeded`.

Код в исходной спеке: `R-GRD-10`.

**Consequences (testable):**
- Превышен лимит шагов: когда агент сделал `max_steps` шагов и не завершил задачу, тогда запуск завершается со статусом `limit_exceeded` и частичным итогом.
- Превышено время: когда запуск идёт дольше `timeout_s`, тогда статус `limit_exceeded` с причиной `timeout`.
- Простой: когда нет событий дольше `idle_s`, тогда запуск останавливается и освобождает слот.

#### FR-120: Иерархия бюджетов токенов и денег

Система SHALL ограничивать расход на уровнях: вызов модели (max output tokens), запуск (токены и $), задача (`budget.issue` — все запуски цепочки по одной задаче), агент в сутки, проект и команда в месяц; иерархия run ≤ issue ≤ agent_day ≤ project_month принудительная (Runner перед выдачей запуска и шлюз LiteLLM на каждом вызове), а не рекомендательная. Бюджет задачи дополняет защиту от зацикливания (R&D, FR-118): цепочка из многих запусков не должна обходить лимит запуска. AD-27. При 80% лимита SHALL отправляться предупреждение, при 100% новый вызов или запуск MUST отклоняться (G1 до старта, G4 на каждом вызове).

Код в исходной спеке: `R-GRD-11`.

**Consequences (testable):**
- Исчерпан дневной бюджет агента: когда расход агента за сутки достиг лимита, тогда новые запуски отклоняются со статусом `limit_exceeded`, активный запуск останавливается после текущего шага.
- Порог предупреждения: когда расход проекта за месяц достиг 80% лимита, тогда администратор получает уведомление, запуски продолжаются.
- Исчерпан бюджет задачи: когда запуски цепочки по одной задаче потратили `budget.issue`, а остальные бюджеты не исчерпаны, тогда новый запуск по задаче не выдаётся, текущий останавливается после шага со статусом `limit_exceeded`, задача идёт по переходу при ошибке, владелец процесса получает уведомление.
- Бюджет задачи выше бюджета агента: когда `budget.issue` задан больше остатка суточного бюджета агента, тогда действует меньший остаток: запуск отклоняется по `agent_day`, при сохранении настройки показано предупреждение об иерархии.
- Превышен бюджет запуска: когда запуск потратил лимит токенов, тогда останавливается после текущего шага со статусом `limit_exceeded`.

#### FR-121: Аномальный расход

Harness SHALL приостанавливать запуск на подтверждение человека, если расход токенов одного шага превышает порог (по умолчанию в 5 раз больше медианы шагов этого запуска или абсолютный предел).

Код в исходной спеке: `R-GRD-12`.

**Consequences (testable):**
- Скачок расхода: когда один шаг потратил в 6 раз больше токенов, чем медиана, тогда запуск переходит в `waiting_approval` с причиной «аномальный расход».
- Обычный шаг: когда шаг потратил столько же, сколько медиана, тогда пауза не нужна.
- Первые шаги: когда медианы ещё нет (меньше 3 шагов), тогда срабатывает только абсолютный предел.

#### FR-122: Circuit breaker на ошибки

Harness MUST останавливать запуск со статусом `failed`, если подряд M вызовов модели или тулов завершились ошибкой (по умолчанию 3); повторы SHALL идти с экспоненциальной задержкой.

Код в исходной спеке: `R-GRD-13`.

**Consequences (testable):**
- Сервис недоступен: когда три вызова MCP подряд вернули ошибку, тогда запуск останавливается с причиной `circuit_open`, а не крутится дальше.
- Единичная ошибка: когда одна ошибка тула, следующий вызов успешен, тогда счётчик сбрасывается, запуск продолжается.
- Повтор с задержкой: когда вторая ошибка подряд, тогда следующий вызов идёт с увеличенной задержкой.

#### FR-123: Лимиты пропускной способности модели

LLM Gateway SHALL ограничивать запросы и токены в минуту на модель и на агента (RPM / TPM); превышение MUST ставить вызов в ожидание или отклонять, а не передавать провайдеру.

Код в исходной спеке: `R-GRD-14`.

**Consequences (testable):**
- Превышен TPM модели: когда суммарный поток токенов к модели превысил TPM, тогда новые вызовы ждут освобождения окна или отклоняются с ошибкой лимита.
- В пределах лимита: когда поток токенов ниже TPM, тогда вызовы проходят без задержки.
- Лимит агента: когда агент превысил свой RPM, модель свободна, тогда вызовы этого агента ждут, другие агенты не затронуты.

#### FR-124: Аварийная остановка

Администратор SHALL иметь kill switch на уровне агента и всей платформы: новые запуски не принимаются, активные останавливаются после текущего шага.

Код в исходной спеке: `R-GRD-15`.

**Consequences (testable):**
- Остановка платформы: когда администратор включил глобальный kill switch, тогда очередь не выдаёт запуски, активные завершаются со статусом `canceled`.
- Kill switch агента: когда включён kill switch одного агента, тогда останавливаются только его запуски.
- Снятие остановки: когда администратор выключил kill switch, тогда очередь снова выдаёт запуски.

#### FR-125: Аудит срабатываний

Каждое срабатывание guardrail SHALL логироваться с ID точки, правилом, агентом и `run_id`.

Код в исходной спеке: `R-GRD-16`.

**Consequences (testable):**
- Разбор отказа: когда администратор ищет причину отказа в запуске, тогда находит сработавшее правило и точку G1–G4.
- Срабатывание в чате запуска: когда G2 отклонил тул, тогда в чате запуска в задаче событие с точкой, правилом и причиной.
- Хранение аудита: когда срок хранения событий истёк, тогда агрегаты срабатываний сохраняются.

#### FR-126: Конфигурация модуля

Модуль SHALL брать свои параметры (16, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9), L1 (S2), L0 (S8): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-GRD-17`.

**Consequences (testable):**
- Значение по умолчанию: когда `opa.cache_ttl_s` (кэш решения OPA для одинакового входа в запуске) не задан в конфигурации, тогда применяется значение по умолчанию: 60.
- Выше максимума: когда `opa.cache_ttl_s` задан больше 300, тогда значение отклонено, ошибка называет `opa.cache_ttl_s` и границы 0–300.
- Граница от другого параметра: когда `loop.no_progress_steps` задан больше, чем `limits.max_steps`, тогда значение отклонено: `loop.no_progress_steps` не может быть больше `limits.max_steps`.

#### FR-127: Хранилища данных

Модуль SHALL хранить свои данные только в S11 (OPA в памяти (bundle)) (`interfaces.md`); данные S2, S8, S9 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-GRD-18`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет правила и данные для решений, тогда запись попадает в S11 (OPA в памяти (bundle)).
- S11 недоступно: когда S11 (OPA в памяти (bundle)) не отвечает, тогда по `on_engine_error`: deny (по умолчанию) или allow с пометкой.
- Прямой доступ к БД: когда код guardrails пытается подключиться к БД платформы напрямую, тогда подключение невозможно: в среде нет учётных данных БД и сетевого доступа к ней.

#### FR-128: Интерфейсы обмена

Интерфейсы модуля (I5, I10, I16, I8) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-GRD-19`.

**Consequences (testable):**
- Таймаут I5: когда Agent Runner → OPA (G1) (I5) не ответил за 200 мс, тогда вызов прерывается; повтор: нет → `on_engine_error`.
- Аутентификация I16: когда собеседник по I16 отклонил учётные данные (токен bundle-сервера), тогда вызов не повторяется, событие с причиной.
- Повтор I16 без дублей: когда вызов I16 повторён после сбоя, тогда дубля нет: да.

#### FR-129: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-GRD-20`.

**Consequences (testable):**
- OPA недоступен: когда opa недоступен, тогда по `on_engine_error`: deny (по умолчанию) или allow с пометкой.
- Битый Rego: когда битый rego, тогда OPA остаётся на прежнем bundle.
- Точка выключена: когда точка выключена, тогда проверка не выполняется, запись в лог старта.
- Нет данных правил агента: когда нет данных правил агента, тогда deny всех тулов кроме явно разрешённых в L0.

#### FR-130: Развёртывание

Модуль SHALL разворачиваться так: OPA — Deployment `opa` в `itsaplan-agents`, 2 реплики, Service ClusterIP; Rego — bundle; без ingress. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-GRD-22`.

**Consequences (testable):**
- Установка: когда выполняется `helm install`: OPA — Deployment `opa` в `itsaplan-agents`, 2 реплики, Service ClusterIP; Rego — bundle; без ingress, тогда объекты созданы в своём namespace с заданными requests / limits, проверки готовности зелёные.
- Обновление: когда выходит новая версия образа `opa` (2 реплики), тогда `opa` заменяется по одной реплике; работа, начатая на старой версии, доделывается.
- Нехватка ресурсов: когда узлу не хватает ресурсов для пода `opa`, тогда под `opa` ждёт размещения, событие эксплуатации.

#### FR-131: Каталог ограничений деградации обучения

Система SHALL хранить каталог ограничений О1–О15 как политику (данные, не код) и включать каждое ограничение отдельно с параметрами: гейт регрессии (О4, `learning.regression_threshold`), TTL (О11), карантин N (О12), лимит размера плейбука (О13), верификатор при записи (О5), «память — справка» (О1), скрытые тесты (О6), ревью тулов (О8), автооткат (О14). По умолчанию включены О1–О9, О11, О12, О14, О15; О10 выключено. Администратор MAY зафиксировать ограничение, проект его тогда не меняет. Новое ограничение добавляется политикой без релиза и вступает в силу ≤ 5 минут.

Код в исходной спеке: `R-GRD-23`.

**Consequences (testable):**
- Добавление ограничения без релиза: когда Безопасность добавляет новое ограничение в каталог политикой, тогда оно действует ≤ 5 минут, правок кода ядра нет.
- Ограничение по умолчанию: когда агенту включают обучение без ручной настройки ограничений, тогда О1–О9, О11, О12, О14, О15 включены, О10 выключено.
- Зафиксировано администратором: когда владелец проекта пытается выключить зафиксированное О4, тогда отказ с названием ограничения и уровня, зафиксировавшего его.

#### FR-132: Потолок стоимости обучения

Система SHALL учитывать затраты на обучение (циклы извлечения, оптимизации, регрессионные прогоны) отдельно от затрат на задачи и задавать для них потолок `learning.cost_ceiling_usd`; при превышении новые циклы обучения MUST блокироваться не позже следующего запуска, аномалия расхода вызывает алерт.

Код в исходной спеке: `R-GRD-24`.

**Consequences (testable):**
- Потолок достигнут: когда расход на обучение превысил потолок, тогда новый цикл обучения не стартует, блокировка наступила не позднее одного запуска после превышения.
- Бюджет проекта не задан: когда владелец включает режим обучения выше off, а `budget.project_month` не задан (потолок по умолчанию — 10% от него), тогда сохранение отклонено, ошибка называет `budget.project_month`.
- Аномалия расхода: когда расход на обучение за сутки вырос аномально, тогда администратор получает алерт.

#### FR-133: Условия режимов выше «предлагать» и применение под контролем человека

Система SHALL не допускать режим `apply_gated` у вида, пока не включены О4, О12 и О14; применение изменения выше порога риска (О15) и применение созданного агентом-инструментальщиком тула MUST требовать одобрения человека; каждое применение MUST иметь трассу (источник, исход, версия, кто утвердил).

Код в исходной спеке: `R-GRD-25`.

**Consequences (testable):**
- Нет обязательных ограничений: когда владелец включает `apply_gated`, а О12 выключено, тогда сохранение отклонено, ошибка называет О12.
- Применение без одобрения: когда изменение выше порога риска применяется без одобрения человека, тогда применение заблокировано, в журнале причина.
- Трасса применения: когда инженер ищет, откуда взялось правило агента, тогда по записи находятся источник, исход, версия и утвердивший за ≤ 5 минут.
- Тул инструментальщика: когда агент-инструментальщик создал тул, тогда тул не доступен агентам, пока человек не провёл ревью (О8) и не применил его.

### 4.9 llm-gateway

**Description:** Единственная точка выхода агентов к LLM-провайдерам: маршрутизация по алиасам моделей, учёт и лимиты токенов, fallback и применение G4. Обоснование: R&D.

**Functional Requirements:**

#### FR-134: Алиасы моделей

Агенты SHALL обращаться к моделям по алиасам; соответствие алиаса провайдеру и модели MUST настраиваться в шлюзе без изменения агентов.

Код в исходной спеке: `R-LLM-01`.

**Consequences (testable):**
- Перенаправление алиаса: когда администратор переназначает алиас на другую модель, тогда новые вызовы по алиасу идут в новую модель.
- Неизвестный алиас: когда агент обращается к несуществующему алиасу, тогда вызов отклоняется с ошибкой алиаса.
- Смена во время запуска: когда алиас переназначен, пока идёт запуск, тогда следующие вызовы запуска идут в новую модель, событие пишется в чат запуска.

#### FR-135: Учёт токенов

Шлюз SHALL учитывать токены и стоимость каждого вызова с привязкой к агенту и `run_id`.

Код в исходной спеке: `R-LLM-02`.

**Consequences (testable):**
- Подсчёт по запуску: когда запуск завершён, тогда известны суммарные токены и $ этого запуска.
- Стрим: когда ответ модели пришёл стримом, тогда токены учтены по завершении стрима.
- Ошибка провайдера: когда провайдер вернул ошибку, тогда неуспешный вызов учитывается отдельно, без стоимости ответа.

#### FR-136: Атрибуция затрат

Каждый вызов модели SHALL нести ключ агента и метаданные запуска (`run_id`, задача); вызов без них MUST отклоняться.

Код в исходной спеке: `R-LLM-03`.

**Consequences (testable):**
- Вызов без метаданных: когда приходит вызов без `run_id`, тогда вызов отклоняется, затраты не теряются без привязки.
- Вызов с метаданными: когда вызов содержит `run_id` и задачу, тогда затраты привязаны к запуску и задаче.
- Чужой ключ: когда вызов идёт с ключом другого агента, тогда затраты записываются на агента ключа, событие несоответствия в аудит.

#### FR-137: Mock-модель для разработки

Шлюз SHALL позволять направить алиас на mock-модель со сценарными ответами (текст, вызов тула, ошибка, задержка) без изменения агентов.

Код в исходной спеке: `R-LLM-04`.

**Consequences (testable):**
- Разработка без ключа провайдера: когда алиас `team-default` направлен на mock, тогда агент получает ответы сценария, затраты считаются по сценарию.
- Сценарий с вызовом тула: когда сценарий mock содержит `tool_call`, тогда агент получает корректный `tool_calls`.
- Нет подходящего сценария: когда запрос не совпал ни с одним сценарием, тогда mock возвращает ответ по умолчанию и отмечает это в логе.

#### FR-138: Лимиты

Шлюз MUST отклонять вызовы сверх лимитов токенов, $ или частоты для агента.

Код в исходной спеке: `R-LLM-05`.

**Consequences (testable):**
- Превышен rate limit: когда агент превысил лимит частоты запросов, тогда вызов отклоняется с ошибкой лимита.
- В пределах лимита: когда агент вызывает модель ниже лимитов, тогда вызов проходит.
- Исчерпан бюджет ключа: когда бюджет virtual key исчерпан, тогда вызов отклоняется до обращения к провайдеру.

#### FR-139: Fallback

Шлюз SHALL поддерживать резервную модель для алиаса на случай недоступности основной.

Код в исходной спеке: `R-LLM-06`.

**Consequences (testable):**
- Провайдер недоступен: когда основная модель вернула ошибку недоступности, тогда запрос выполняется резервной моделью, факт фиксируется в трейсе.
- Резерв не задан: когда основная модель недоступна, fallback не настроен, тогда вызов завершается ошибкой, Harness применяет повтор.
- Резерв тоже недоступен: когда основная и резервная модели недоступны, тогда ошибка `all_providers_failed`.

#### FR-140: Несколько провайдеров

Шлюз SHALL поддерживать облачных провайдеров и локальные модели через единый интерфейс.

Код в исходной спеке: `R-LLM-07`.

**Consequences (testable):**
- Локальная модель: когда алиас агента указывает на локальную модель, тогда агент работает без изменений в своём определении.
- Облачный провайдер: когда алиас указывает на облачную модель, тогда агент работает без изменений.
- Нет ключа провайдера: когда у провайдера не задан ключ, тогда алиас помечен недоступным, вызов отклоняется.

#### FR-141: Конфигурация модуля

Модуль SHALL брать свои параметры (6, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9 (`litellm config.yaml`)), L1 (S6): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-LLM-08`.

**Consequences (testable):**
- Значение по умолчанию: когда `drop_params` (отбрасывать параметры, которые модель не…) не задан в конфигурации, тогда применяется значение по умолчанию: true.
- Граница от другого параметра: когда `key.max_budget` задан больше, чем `budget.daily_usd`, тогда значение отклонено: `key.max_budget` не может быть больше `budget.daily_usd`.
- Недопустимое значение: когда `fallbacks` задан вне допустимых значений (нет … список алиасов), тогда значение отклонено, ошибка называет `fallbacks` и допустимые значения.

#### FR-142: Хранилища данных

Модуль SHALL хранить свои данные только в S6 (PostgreSQL 17 (тот же кластер), БД `litellm`) (`interfaces.md`); данные S9 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-LLM-09`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет virtual keys, бюджеты, журнал затрат, тогда запись попадает в S6 (PostgreSQL 17 (тот же кластер), БД `litellm`).
- S6 недоступно: когда S6 (PostgreSQL 17 (тот же кластер), БД `litellm`) не отвечает, тогда проверка бюджетов невозможна — вызовы отклоняются.
- Доступ вне своих хранилищ: когда код llm-gateway обращается к таблицам вне S6, тогда доступа нет: роль БД llm-gateway ограничена S6.

#### FR-143: Интерфейсы обмена

Интерфейсы модуля (I8, I13, I14, I15, I22) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-LLM-10`.

**Consequences (testable):**
- Таймаут I8: когда Harness → LiteLLM (I8) не ответил за 120 с, тогда вызов прерывается; повтор: 2 раза с backoff.
- Аутентификация I13: когда собеседник по I13 отклонил учётные данные (ключ провайдера в LiteLLM (Secret)), тогда вызов не повторяется, событие с причиной.
- Повтор I8 без дублей: когда вызов I8 повторён после сбоя, тогда дубля нет: да по результату: побочных действий нет; повтор стоит токенов и учитывается в бюджете.

#### FR-144: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-LLM-11`.

**Consequences (testable):**
- Провайдер недоступен: когда провайдер недоступен, тогда fallback-модель; если нет — ошибка вызова.
- БД `litellm` недоступна: когда бд `litellm` недоступна, тогда проверка бюджетов невозможна — вызовы отклоняются.
- Нет ключа провайдера: когда нет ключа провайдера, тогда алиас недоступен.
- LiteLLM упал: когда litellm упал, тогда вызовы Harness получают ошибку, circuit breaker.

#### FR-145: Развёртывание

Модуль SHALL разворачиваться так: LiteLLM — Deployment `litellm` в `itsaplan-agents`, 2 реплики за Service ClusterIP; БД `litellm` через PgBouncer; админка без ingress. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-LLM-13`.

**Consequences (testable):**
- Установка: когда выполняется `helm install`: LiteLLM — Deployment `litellm` в `itsaplan-agents`, 2 реплики за Service ClusterIP; БД `litellm` через PgBouncer; админка без ingress, тогда объекты созданы в своём namespace с заданными requests / limits, проверки готовности зелёные.
- Обновление: когда выходит новая версия образа `litellm` (2 реплики), тогда `litellm` заменяется по одной реплике; работа, начатая на старой версии, доделывается.
- Нехватка ресурсов: когда узлу не хватает ресурсов для пода `litellm`, тогда под `litellm` ждёт размещения, событие эксплуатации.

### 4.10 observability

**Description:** Прозрачность работы агентов: пошаговые события запуска, затраты токенов и денег, события guardrails — для пользователя задачи, отладки и аудита. Обоснование: R&D.

**Functional Requirements:**

#### FR-146: События запуска

Система SHALL записывать события каждого запуска в формате AG-UI (запуск, шаги, реплики, рассуждения, вызовы тулов, план) и события платформы как `CUSTOM` (вопрос, подтверждение, guardrail, память, вызов LLM) в БД с привязкой к `run_id` и задаче (AD-21).

Код в исходной спеке: `R-OBS-01`.

**Consequences (testable):**
- Разбор запуска: когда администратор открывает запуск по `run_id`, тогда видит последовательность шагов с входами, выходами (в пределах `events.level`) и временем.
- Чувствительные данные: когда аргументы тула содержат секрет, тогда в событии значение маскируется.
- БД событий недоступна: когда запись события не удалась, тогда Runner буферизует и дописывает события позже.
- Дельты сообщения: когда приходят `TEXT_MESSAGE_CONTENT` или `REASONING_MESSAGE_CONTENT` по одному сообщению, тогда в БД сохраняется одно собранное сообщение на `*_END`, дельты уходят только в живой поток.

#### FR-147: Чат запуска в задаче

Пользователь задачи SHALL видеть в задаче ICPlan чат запуска (AD-21): реплики агента, свёрнутые рассуждения и вызовы тулов, план, вопросы и подтверждения с кнопками, свои указания и карточку итога с критериями; лента обновляется без перезагрузки.

Код в исходной спеке: `R-OBS-02`.

**Consequences (testable):**
- Ход выполнения: когда агент работает над задачей, тогда в задаче появляются шаги по мере выполнения.
- Завершённый запуск: когда пользователь открывает задачу после завершения, тогда видит полный чат запуска и итог.
- Несколько запусков: когда по задаче было три запуска, тогда чат запуска разделён по запускам и агентам.
- Почему агент это делает: когда агент вызывает тул, тогда перед вызовом в ленте есть реплика агента о намерении, а рассуждение модели (если есть) доступно по раскрытию.
- Итог шага: когда запуск завершён, тогда карточка итога показывает результат, артефакты, критерии приёмки ✓ / ✗ и кнопки вердикта шага.
- Агент взял задачу: когда Runner взял запуск из очереди (I1), тогда в чате запуска появляется шаг «агент взял задачу» не позже 10 с после взятия.

#### FR-148: Трассировка

Каждый запуск SHALL хранить задачу, агента, версию определения агента и связь с итогом; по задаче MUST быть доступны все её запуски с событиями.

Код в исходной спеке: `R-OBS-03`.

**Consequences (testable):**
- Разбор задачи: когда администратор открывает задачу, тогда видит все запуски по ней, версии агентов и итоги.
- Запуск без задачи: когда запуск по расписанию без задачи, тогда трассировка идёт по агенту и расписанию.
- Удалённый агент: когда агент удалён, запуски остались, тогда история показывает агента и версию на момент запуска.

#### FR-149: Маскирование чувствительных данных

Перед записью события система MUST маскировать секреты и персональные данные в аргументах и ответах: по полям из подключённых секретов и по шаблонам (ключи API, токены, e-mail, телефоны). Исходные значения MUST NOT попадать в хранилище событий. Источник: US-OBS-03.

Код в исходной спеке: `R-OBS-04`.

**Consequences (testable):**
- Ключ в аргументах тула: когда аргументы тула содержат строку, похожую на ключ API, тогда в событии значение заменено на `***`.
- Значение подключённого секрета: когда ответ тула содержит значение секрета, подставленного прокси, тогда значение маскируется, даже если не совпадает с шаблонами.
- Нет чувствительных данных: когда событие не содержит секретов и персональных данных, тогда событие записывается без изменений.
- Секрет в промпте: когда промпт или ответ модели содержит значение секрета или персональные данные, тогда значение маскируется до записи события; полный текст без секрета сохраняется.

#### FR-150: Затраты

Система SHALL агрегировать токены и $ по запуску, задаче, агенту, модели и периоду.

Код в исходной спеке: `R-OBS-05`.

**Consequences (testable):**
- Отчёт по модели: когда запрашиваются затраты по модели за месяц, тогда возвращается сумма по всем агентам, использовавшим модель.
- Затраты задачи: когда открыта задача с тремя запусками, тогда показана сумма токенов и $ по задаче.
- Нет данных о цене: когда у модели не задана цена, тогда токены учтены, стоимость помечена «неизвестна».

#### FR-151: Политика хранения

События запусков MUST храниться в пределах настраиваемого срока и удаляться по его истечении; агрегаты затрат SHALL сохраняться.

Код в исходной спеке: `R-OBS-06`.

**Consequences (testable):**
- Истёк срок: когда срок хранения событий истёк, тогда события удалены, агрегаты затрат сохранены.
- Срок не истёк: когда событию 10 дней при сроке 90, тогда событие доступно.
- Изменён срок: когда срок хранения уменьшен, тогда старые события удаляются при следующей очистке.

#### FR-152: Сводка и статистика агентов

Observability SHALL отдавать сводку по задачам с агентами (в работе, в очереди, ждут человека, открыто, закрыто, время в работе и в ожидании, токены и $), стоимость на принятую задачу и причины возвратов цепочки (AD-27) и статистику агентов (запуски, успешные, возвращённые пользователем, среднее время, затраты) с фильтром по проекту, пользователю, агенту и периоду — из `agent_run`, событий запуска и затрат LiteLLM.

Код в исходной спеке: `R-OBS-13`.

**Consequences (testable):**
- Сводка пользователя: когда пользователь открыл «Мои задачи с агентами» за неделю, тогда видны счётчики по состояниям, время и затраты по задачам.
- Статистика агента: когда администратор открыл статистику агента за месяц, тогда запуски, доля успешных и возвращённых, среднее время, затраты.
- Стоимость на принятую задачу: когда администратор открыл статистику процесса за месяц, тогда видна стоимость на принятую задачу (все роли, возвраты и оркестрация) по задаче, процессу и роли; процессы из одного шага помечены как базовая линия.
- Возвраты и круги: когда администратор открыл статистику цепочки, тогда видны доли причин возвратов (`defect`, `spec_question`, `blocked`), число кругов на задачу и блокировки по бюджету и лимитам цепочки.
- Надёжность на эталонном наборе: когда прогнан эталонный набор задач не менее трёх раз, тогда показан pass^k по набору для каждого варианта (один агент, цепочка).
- Затраты недоступны: когда LiteLLM недоступен, тогда сводка без затрат с пометкой, остальное показано.

#### FR-153: Стоимость на принятую задачу с учётом обучения

Observability SHALL включать в стоимость на принятую задачу затраты на обучение (токены и $ циклов извлечения, оптимизации и регрессионных прогонов), показывать их отдельной строкой и разбивать статистику процесса по эффективному режиму обучения («без обучения», факты, плейбук, все виды) для сравнения на эталонном наборе (≥ 3 прогона).

Код в исходной спеке: `R-OBS-14`.

**Consequences (testable):**
- Обучение отдельной строкой: когда администратор открывает стоимость на принятую задачу агента с включённым обучением, тогда итог включает затраты на обучение, токены обучения видны отдельно от токенов задач.
- Сравнение режимов: когда инженер сравнивает режимы «без обучения» и «факты» за период, тогда видны стоимость на принятую задачу, доля принятых и число прогонов по каждому режиму.

#### FR-154: Конфигурация модуля

Модуль SHALL брать свои параметры (3, таблица «Параметры модуля» в `interfaces.md`) с уровней L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-OBS-07`.

**Consequences (testable):**
- Значение по умолчанию: когда `events.level` (детализация событий) не задан в конфигурации, тогда применяется значение по умолчанию: всё.
- Выше максимума: когда `retention_days` задан больше 365, тогда значение отклонено, ошибка называет `retention_days` и границы 7–365.
- Недопустимое значение: когда `events.level` задан вне допустимых значений (итоги … всё), тогда значение отклонено, ошибка называет `events.level` и допустимые значения.

#### FR-155: Хранилища данных

Модуль SHALL хранить свои данные только в S3 (Postgres ICPlan, схема `platform`) (`interfaces.md`); данные S6 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-OBS-08`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет события запусков (`run_event`), тогда запись попадает в S3 (Postgres ICPlan, схема `platform`).
- S3 недоступно: когда S3 (Postgres ICPlan, схема `platform`) не отвечает, тогда события буферизуются у Runner, запуск продолжается; чат запуска временно неполный.
- Доступ вне своих хранилищ: когда код observability обращается к таблицам вне S3, тогда доступа нет: роль БД observability ограничена S3.

#### FR-156: Интерфейсы обмена

Интерфейсы модуля (I2, I14, I20, I22) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-OBS-09`.

**Consequences (testable):**
- Таймаут I2: когда Agent Runner → ICPlan (шаги, итог) (I2) не ответил за 10 с, тогда вызов прерывается; повтор: повтор с дедупликацией по (run_id, seq).
- Аутентификация I14: когда собеседник по I14 отклонил учётные данные (пароль из Secret), тогда вызов не повторяется, событие с причиной.
- Повтор I2 без дублей: когда вызов I2 повторён после сбоя, тогда дубля нет: да, по (run_id, seq).

#### FR-157: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-OBS-10`.

**Consequences (testable):**
- Нет записи событий: когда нет записи событий, тогда буфер в Runner, досылка.
- Нет цены модели: когда нет цены модели, тогда токены учтены, стоимость «неизвестна».
- Переполнение таблицы событий: когда переполнение таблицы событий, тогда очистка по сроку, предупреждение эксплуатации; уровень детализации меняет только эксплуатация (`events.level`).

#### FR-158: Развёртывание

Модуль SHALL разворачиваться так: таблица событий в Postgres; чтение — через api ICPlan; Langfuse / Prometheus — бэклог. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-OBS-12`.

**Consequences (testable):**
- Установка в составе ICPlan: когда разворачивается релиз ICPlan (таблица событий в Postgres; чтение — через api ICPlan; Langfuse / Prometheus — бэклог) с модулем observability, тогда миграции observability применены до старта `api`, модуль доступен в ICPlan.
- Обновление: когда выходит новая версия форка ICPlan с изменениями observability, тогда миграции observability обратно совместимы, `api` обновляется по одной реплике без простоя.
- Откат: когда версия с изменениями observability не прошла проверки готовности, тогда Helm откатывает ревизию, данные observability сохранены.

### 4.11 platform-infrastructure

**Description:** Инфраструктура платформы: профиль нагрузки и ёмкость, кластер Kubernetes (k3s), упаковка Helm, ingress и балансировка, СУБД и пул соединений, объектное хранилище, секреты, резервное копирование, сетевые политики, локальная среда. Обоснование: R&D.

**Functional Requirements:**

#### FR-159: Кластер Kubernetes

Платформа SHALL разворачиваться в k3s на одном узле с разделением по namespaces: `itsaplan-core` (ICPlan), `itsaplan-data` (Postgres, PgBouncer, RustFS), `itsaplan-agents` (Runner, LiteLLM, OPA, Memory, egress-прокси, запуски), `itsaplan-platform` (бэклог: мониторинг, Gitea).

Код в исходной спеке: `R-INF-02`.

**Consequences (testable):**
- Установка с нуля: когда администратор запускает установку на чистом сервере, тогда k3s установлен, namespaces созданы, все сервисы готовы.
- Ресурс в чужом namespace: когда сервис агента пытается создать объект в `itsaplan-core`, тогда операция отклонена правами ServiceAccount.
- Повторная установка: когда установку запускают повторно на работающем кластере, тогда изменения применяются без пересоздания данных.
- Защита узла: когда на узле выполнена проверка kube-bench, тогда критичных несоответствий CIS нет.

#### FR-160: Упаковка и развёртывание Helm

Каждый компонент SHALL разворачиваться Helm-чартом с версией; значения окружения — в `values-<среда>.yaml`, секреты — только через `existingSecret`. Обновление MUST выполняться без простоя для сервисов с ≥ 2 репликами.

Код в исходной спеке: `R-INF-03`.

**Consequences (testable):**
- Обновление версии: когда администратор обновляет чарт LiteLLM на новую версию, тогда реплики заменяются по одной, вызовы агентов не прерываются.
- Откат: когда новая версия не проходит проверки готовности, тогда выполняется откат на предыдущую ревизию релиза.
- Секрет в values: когда в `values.yaml` указано значение секрета, тогда установка отклоняется проверкой чарта.

#### FR-161: Ingress и TLS

Публичный вход SHALL идти только через Traefik по HTTPS с сертификатом ACME: `web`, `api`, `/mcp`. Админки (LiteLLM, OPA, Memory API, базы) MUST NOT иметь публичного ingress.

Код в исходной спеке: `R-INF-04`.

**Consequences (testable):**
- Вход пользователя: когда пользователь открывает адрес ICPlan, тогда запрос идёт по HTTPS через Traefik к `web`.
- Попытка открыть админку: когда запрос снаружи идёт на адрес LiteLLM, тогда маршрута нет, ответ 404.
- HTTP без TLS: когда запрос пришёл по HTTP, тогда выполняется перенаправление на HTTPS.

#### FR-162: Балансировка между репликами

Сервисы с несколькими репликами SHALL получать трафик через Service (ClusterIP) с проверками готовности; реплика, не прошедшая проверку, MUST исключаться из балансировки.

Код в исходной спеке: `R-INF-05`.

**Consequences (testable):**
- Реплика не готова: когда одна из двух реплик LiteLLM не проходит readiness, тогда трафик идёт только на здоровую реплику.
- Все реплики готовы: когда обе реплики OPA готовы, тогда запросы распределяются между ними.
- Нет готовых реплик: когда ни одна реплика сервиса не готова, тогда клиенты получают ошибку соединения и действуют по FMEA своей спеки.

#### FR-163: СУБД и пул соединений

Данные SHALL храниться в одном кластере PostgreSQL 17 (CloudNativePG) с БД `itsaplan` (схемы `public`, `platform`, `harness_ckpt`) и БД `litellm`; клиенты MUST подключаться через PgBouncer (transaction pooling, не более 30 серверных соединений).

Код в исходной спеке: `R-INF-06`.

**Consequences (testable):**
- Рост числа клиентов: когда 60 клиентских соединений открыто одновременно, тогда Postgres держит не более 30 серверных соединений, запросы обслуживаются.
- Сессионная функция: когда клиенту нужна функция уровня сессии (LISTEN / NOTIFY), тогда он подключается к отдельному session-пулу или напрямую, по согласованному списку.
- Миграции: когда выходит новая версия ICPlan с миграциями, тогда миграции выполняются до старта новых реплик, схема `platform` не затрагивается.

#### FR-164: Объектное хранилище

Вложения, артефакты и резервные копии SHALL храниться в S3-совместимом хранилище RustFS; клиенты MUST использовать только S3 API, чтобы хранилище можно было заменить (например, на SeaweedFS) без изменения кода.

Код в исходной спеке: `R-INF-07`.

**Consequences (testable):**
- Загрузка вложения: когда агент публикует артефакт в задачу, тогда файл сохранён в бакете `planner-attachments`.
- Замена хранилища: когда RustFS заменяется другим S3-совместимым хранилищем, тогда меняются только адрес и ключи в конфигурации.
- Хранилище недоступно: когда RustFS не отвечает, тогда итог публикуется без вложений, загрузка повторяется.

#### FR-165: Резервное копирование

Postgres SHALL резервироваться базовыми копиями и непрерывным архивом WAL во внешнее S3-хранилище на другой площадке (AD-18); объектное хранилище MUST копироваться туда же. Восстановление MUST проверяться не реже раза в месяц.

Код в исходной спеке: `R-INF-08`.

**Consequences (testable):**
- Потеря узла: когда узел утрачен вместе с диском, тогда данные восстанавливаются из копий вне узла.
- Проверка восстановления: когда выполняется ежемесячная проверка, тогда копия восстанавливается в отдельный namespace, результат записан.
- Копия не создалась: когда резервная копия не создана по расписанию, тогда администратор получает предупреждение.

#### FR-166: Секреты

Секреты SHALL храниться только в Kubernetes Secret (создаются скриптом из локального `.env`, вне git) и подключаться через `existingSecret`; в git, values и образах их MUST NOT быть.

Код в исходной спеке: `R-INF-09`.

**Consequences (testable):**
- Новый секрет: когда администратор добавляет ключ провайдера, тогда он попадает в Secret, сервис перечитывает его без пересборки образа.
- Секрет в репозитории: когда в коммит попадает значение секрета, тогда проверка перед коммитом его останавливает.
- Секрета нет: когда обязательный Secret отсутствует, тогда сервис не стартует, ошибка называет Secret.

#### FR-167: Сетевые политики

Трафик между namespaces SHALL быть запрещён по умолчанию и разрешён только по списку интерфейсов (I1–I23); контейнеры запусков MUST выходить наружу только через egress-прокси.

Код в исходной спеке: `R-INF-10`.

**Consequences (testable):**
- Разрешённый интерфейс: когда Runner обращается к API ICPlan, тогда соединение разрешено политикой.
- Запрещённый маршрут: когда контейнер запуска пытается подключиться к Postgres напрямую, тогда соединение блокируется.
- Новый интерфейс: когда добавлен новый интерфейс в `interfaces.md`, тогда политика дополняется до выпуска.

#### FR-168: Проверки готовности и порядок запуска

Каждый сервис SHALL иметь liveness и readiness проверки; зависимые сервисы MUST NOT принимать трафик, пока их обязательные зависимости (БД, секреты) не готовы.

Код в исходной спеке: `R-INF-11`.

**Consequences (testable):**
- Холодный старт: когда кластер запускается после остановки, тогда сначала готовы Postgres и PgBouncer, затем api, LiteLLM, OPA, затем Runner.
- Зависимость пропала: когда Postgres недоступен у работающего api, тогда api перестаёт быть готовым, ingress не шлёт на него трафик.
- Зависший процесс: когда процесс не отвечает на liveness, тогда под перезапускается.

#### FR-169: Локальная среда

Для разработки SHALL поддерживаться две локальные среды: docker compose (этапы 1–2) и k3d с теми же чартами (этап 4); образы и версии MUST совпадать с серверными.

Код в исходной спеке: `R-INF-12`.

**Consequences (testable):**
- Разработка Harness: когда разработчик запускает compose, тогда поднимаются ICPlan, Postgres, RustFS, LiteLLM с mock.
- Проверка чартов: когда разработчик разворачивает чарты в k3d, тогда результат совпадает с серверной установкой, кроме адресов и ресурсов.
- Расхождение версий: когда версия образа в compose отличается от чарта, тогда проверка согласованности сообщает о расхождении.

#### FR-170: Конфигурация модуля

Параметры SHALL задаваться в Helm values (S9, таблица «Параметры модуля» в `interfaces.md`) и проверяться схемой `values.schema.json` по границам «Мин»–«Макс»; изменение применяется `helm upgrade` с поочерёдной заменой реплик. Версии компонентов MUST быть закреплены явно.

Код в исходной спеке: `R-INF-13`.

**Consequences (testable):**
- Значение вне схемы: когда в values `<сервис>.replicas` меньше 1, тогда `helm upgrade` отклонён схемой с именем параметра и границей.
- Изменение через helm upgrade: когда в values изменено `<сервис>.replicas` с 1 на 2, тогда реплики добавлены без простоя, проверки готовности зелёные.
- Версия не закреплена: когда в values не указан `k3s.version` или тег образа, тогда установка отклонена: версия обязательна.

#### FR-171: Хранилища данных

Модуль SHALL хранить свои данные только в S7 (RustFS (S3 API), бакет `planner-attachments`) (`interfaces.md`); данные S1, S6, S9 — доступ только через API или конфигурацию владельца. Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-INF-14`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет вложения задач, артефакты агентов, резервные копии, тогда запись попадает в S7 (RustFS (S3 API), бакет `planner-attachments`).
- S7 недоступно: когда S7 (RustFS (S3 API), бакет `planner-attachments`) не отвечает, тогда вложения и артефакты не сохраняются, итоги публикуются без вложений; копии БД вне площадки не затронуты.
- Прямой доступ к БД: когда код platform-infrastructure пытается подключиться к БД платформы напрямую, тогда подключение невозможно: в среде нет учётных данных БД и сетевого доступа к ней.

#### FR-172: Интерфейсы обмена

Интерфейсы модуля (I21, I22, I23, I19) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-INF-15`.

**Consequences (testable):**
- Таймаут I21: когда Пользователи → Traefik → web / api / mcp (I21) не ответил за 60 с (ingress), тогда вызов прерывается; повтор: нет.
- Аутентификация I22: когда собеседник по I22 отклонил учётные данные (логин / пароль из Secret, роль на схему), тогда вызов не повторяется, событие с причиной.
- Неидемпотентный вызов I23: когда вызов I23 (Agent Runner → Kubernetes API (этап 4)) прервался сбоем сети, тогда автоматического повтора нет, решение принимает вызывающий.

#### FR-173: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-INF-16`.

**Consequences (testable):**
- Узел недоступен: когда узел недоступен, тогда вся платформа недоступна (один узел).
- Postgres недоступен: когда postgres недоступен, тогда сервисы не готовы, запуски не стартуют.
- PgBouncer исчерпал пул: когда pgbouncer исчерпал пул, тогда запросы ждут до таймаута, ошибка с причиной.
- Истёк TLS-сертификат: когда истёк tls-сертификат, тогда Traefik обновляет по ACME; при сбое — предупреждение.
- Переполнен диск: когда переполнен диск (метрика диска), тогда запись в БД и хранилище останавливается; очистка по срокам, расширение диска.

#### FR-174: Развёртывание

Модуль SHALL разворачиваться так: k3s один узел; namespaces `itsaplan-core`, `itsaplan-data`, `itsaplan-agents`, `itsaplan-platform`; Traefik ingress; CloudNativePG + PgBouncer; RustFS. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-INF-18`.

**Consequences (testable):**
- Установка платформы: когда выполняется установка: k3s один узел; namespaces `itsaplan-core`, `itsaplan-data`, `itsaplan-agents`, `itsaplan-platform`; Traefik ingress; CloudNativePG + PgBouncer; RustFS, тогда компоненты подняты в порядке проверок готовности.
- Обновление компонента: когда обновляется чарт компонента, тогда замена по одной реплике, проверки готовности зелёные.
- Нехватка ёмкости: когда узлу не хватает ресурсов для пода, тогда под ждёт размещения, предупреждение эксплуатации.

#### FR-175: Изоляция сред

Среды dev, CI, staging и prod SHALL иметь изолированные Kubernetes namespaces, базы данных и учётные данные; workload одной среды MUST NOT получать доступ к данным и секретам другой среды. Конкретная кластерная топология и числовой потолок staging задаются отдельно.

Код в исходной спеке: `R-INF-19`.

**Consequences (testable):**
- Развёртывание среды: когда администратор разворачивает сервисы в одной из сред, тогда сервисы используют namespace, базу данных и учётные данные этой среды, не общие с другими средами.
- Межсредовой доступ: когда workload пытается подключиться к базе данных или прочитать Kubernetes Secret другой среды, тогда доступ отклонён.
- Конфигурация с чужим ресурсом: когда манифест развёртывания ссылается на базу данных или Secret другой среды, тогда проверка конфигурации отклоняет развёртывание до запуска workload.

### 4.12 tool-integration

**Description:** Подключение тулов и MCP-серверов к агентам через Registry, чтобы расширять возможности агентов без изменения кода платформы. Обоснование: R&D.

**Functional Requirements:**

#### FR-176: Регистрация MCP-сервера

Система SHALL позволять зарегистрировать MCP-сервер в Registry и подключить его к агенту ссылкой в определении.

Код в исходной спеке: `R-MCP-01`.

**Consequences (testable):**
- Новый MCP-сервер: когда администратор регистрирует MCP-сервер и добавляет его агенту, тогда при следующем запуске тулы сервера доступны агенту.
- Недоступный сервер: когда регистрируемый сервер не отвечает, тогда регистрация сохраняется с пометкой «недоступен», агенту тулы не выдаются.
- Повторная регистрация: когда сервер с тем же адресом уже есть, тогда регистрация отклоняется как дубликат.

#### FR-177: Ограничение набора тулов

Агенту SHALL быть доступны только тулы, явно перечисленные в его определении (допускается подмножество тулов MCP-сервера). Проверка MUST выполняться вне sandbox — в MCP-прокси Agent Runner (AD-19); Harness только фильтрует список для модели.

Код в исходной спеке: `R-MCP-02`.

**Consequences (testable):**
- Тул вне списка: когда LLM запрашивает тул, не входящий в определение агента, тогда вызов отклоняется.
- Тул из списка: когда LLM запрашивает тул из определения, тогда вызов выполняется.
- Новый тул на сервере: когда на MCP-сервере появился тул, которого нет в allowlist, тогда агенту он не виден.
- Вызов в обход Harness: когда код в sandbox обращается к MCP-серверу напрямую, тогда соединение недоступно: MCP-серверы доступны только через MCP-прокси Runner, вызов вне allowlist прокси отклоняет.

#### FR-178: Таймауты и ошибки тулов

Каждый вызов тула MUST иметь таймаут; ошибка или таймаут SHALL возвращаться агенту как результат тула, а не прерывать запуск.

Код в исходной спеке: `R-MCP-03`.

**Consequences (testable):**
- Недоступный MCP: когда MCP-сервер не ответил за таймаут, тогда агент получает ошибку тула и продолжает цикл.
- Успешный вызов: когда тул ответил вовремя, тогда результат возвращается агенту.
- Большой ответ: когда ответ тула больше лимита, тогда ответ обрезается с пометкой, контекст не переполняется.

#### FR-179: Выбор между MCP и прямым вызовом

Тип интеграции SHALL выбираться по правилам: детерминированные последовательности, пакетные операции и внутренние вызовы платформы (Runner↔ICPlan, Harness↔LLM Gateway, проверки G1–G4, автозапись M1/M2) — прямой вызов; действия, которые выбирает модель, — тул агента; тул, нужный нескольким агентам или хранящий секрет вне агента, — MCP-сервер; стабильный тул только для Harness — нативный тул.

Код в исходной спеке: `R-MCP-04`.

**Consequences (testable):**
- Внутренний вызов: когда Agent Runner получает запуск из очереди ICPlan, тогда используется прямой API, а не MCP.
- Тул для нескольких агентов: когда доступ к git-провайдеру нужен нескольким агентам, тогда он подключается как MCP-сервер, секрет хранится на стороне сервера.
- Пакетная операция: когда нужно обработать 500 записей, тогда используется прямой вызов, не тул модели.

#### FR-180: Административные тулы отделены

Административные функции (бюджеты, политики, профили) SHALL отдаваться отдельными MCP-серверами и MUST NOT подключаться рабочим агентам по умолчанию.

Код в исходной спеке: `R-MCP-05`.

**Consequences (testable):**
- Рабочий агент: когда у рабочего агента запрашивается список тулов, тогда административных тулов в нём нет.
- Агент-администратор: когда агенту явно подключён админ-сервер, тогда админ-тулы ему видны, вызовы идут в аудит.
- Попытка вызова: когда рабочий агент пытается вызвать админ-тул по имени, тогда вызов отклоняется.

#### FR-181: Скиллы

Скилл SHALL быть пакетом из инструкций и ссылок на тулы, подключаемым к агенту как единое целое.

Код в исходной спеке: `R-MCP-06`.

**Consequences (testable):**
- Подключение скилла: когда агенту добавлен скилл, тогда агент получает инструкции скилла и его тулы.
- Скилл без тулов: когда скилл содержит только инструкции, тогда агент получает инструкции, набор тулов не меняется.
- Скилл с недоступным тулом: когда тул скилла не входит в allowlist агента, тогда скилл подключается без этого тула, событие-предупреждение.

#### FR-182: MCP-сервер ICPlan

Агент SHALL работать с ICPlan через MCP-сервер `itsaplan-core` (REST API ICPlan как тулы: чтение задачи, комментарий, `update_issue`, создание задач), включённый для проекта, по ключу агента. Для задачи в процессе смена колонки через `update_issue` MUST отклоняться (переход делает ICPlan).

Код в исходной спеке: `R-MCP-13`.

**Consequences (testable):**
- Работа с задачей: когда агент читает задачу и пишет комментарий через `itsaplan-core`, тогда данные и комментарий в задаче, от имени агента.
- MCP выключен в проекте: когда MCP проекта выключен, тогда тулы ICPlan недоступны, запуск завершается с причиной.
- Смена колонки в процессе: когда агент вызывает `update_issue` со сменой колонки задачи в процессе, тогда смена колонки отклонена, остальные поля обновлены.

#### FR-183: Конфигурация модуля

Модуль SHALL брать свои параметры (5, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы.

Код в исходной спеке: `R-MCP-07`.

**Consequences (testable):**
- Значение по умолчанию: когда `servers` (подключённые MCP-серверы) не задан в конфигурации, тогда применяется значение по умолчанию: itsaplan-core.
- Выше максимума: когда `timeout_s` задан больше 300, тогда значение отклонено, ошибка называет `timeout_s` и границы 5–300.
- Нет обязательного поля: когда настройку сохраняют без `auth.secret_ref`, тогда сохранение отклонено, ошибка называет `auth.secret_ref`.

#### FR-184: Хранилища данных

Модуль SHALL хранить свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) (`interfaces.md`). Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-MCP-08`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет MCP-серверы проекта, тулы и навыки, ссылки на секреты, тогда запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`).
- S1 недоступно: когда S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает, тогда тулы ICPlan возвращают ошибку агенту с типом «недоступно»; агент не повторяет записи сам.
- Доступ вне своих хранилищ: когда код tool-integration обращается к таблицам вне S1, тогда доступа нет: роль БД tool-integration ограничена S1.

#### FR-185: Интерфейсы обмена

Интерфейсы модуля (I9, I17) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-MCP-09`.

**Consequences (testable):**
- Таймаут I9: когда Harness → MCP-серверы (I9) не ответил за 30 с, тогда вызов прерывается; повтор: чтение — 2 раза; запись — нет.
- Аутентификация I17: когда собеседник по I17 отклонил учётные данные (allowlist хостов, подстановка секретов), тогда вызов не повторяется, событие с причиной.
- Неидемпотентный вызов I9: когда вызов I9 (Harness → MCP-серверы) прервался сбоем сети, тогда автоматического повтора нет, решение принимает вызывающий.

#### FR-186: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-MCP-10`.

**Consequences (testable):**
- MCP-сервер недоступен: когда mcp-сервер недоступен, тогда ошибка тула агенту.
- Секрет MCP не задан: когда секрет mcp не задан, тогда тулы сервера недоступны агенту, предупреждение.
- Сервер изменил набор тулов: когда сервер изменил набор тулов, тогда новые тулы не видны без allowlist.

#### FR-187: Развёртывание

Модуль SHALL разворачиваться так: MCP `itsaplan-core` — часть api ICPlan; внешние MCP — через egress-прокси. Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-MCP-12`.

**Consequences (testable):**
- MCP ICPlan: когда обновляется api ICPlan с `itsaplan-core`, тогда MCP обновляется вместе с api по одной реплике, тулы доступны без перерыва больше времени переподключения.
- Внешний MCP-сервер: когда подключается новый внешний MCP-сервер, тогда образ сервера закреплён по digest и скопирован в реестр платформы, доступ — через egress-прокси.
- Сервер не готов: когда внешний MCP-сервер не прошёл проверку готовности, тогда его тулы недоступны агентам, событие эксплуатации; остальные серверы работают.

### 4.13 icplan-agent-autopickup

**Description:** Автоматическая работа задачи по процессу в ICPlan: тип задачи задаёт процесс, шаг процесса — колонку и агента, итог запуска — переход на следующий шаг; агент берёт задачи из своей очереди, чтобы процесс шёл без ручного делегирования. Обоснование: R&D.

**Functional Requirements:**

#### FR-188: Агент шага процесса

Шаг процесса SHALL иметь необязательного агента-исполнителя. Когда задача входит в колонку шага своего процесса, ICPlan SHALL сделать агента делегатом задачи и поставить запуск в очередь агента; шаг без агента — ручной, задача ждёт человека.

Код в исходной спеке: `R-AP-01`.

**Consequences (testable):**
- Задача вошла в шаг с агентом: когда задачу типа «Фича» переводят в колонку «Анализ», где у шага процесса «Фича» агент «Аналитик», тогда делегат задачи — «Аналитик», в его очереди появляется запуск.
- Ручной шаг: когда задача входит в колонку, шаг которой без агента, тогда делегат снимается, запуск не создаётся, исполнитель — по автоназначению колонки.
- Агент не участник проекта: когда в шаге процесса указан агент, которого убрали из проекта, тогда запуск не создаётся, в истории предупреждение.

#### FR-189: Тип задачи задаёт процесс

Тип задачи SHALL быть типом процесса: у типа не более одного процесса. При создании задачи этого типа или смене типа на него ICPlan SHALL поставить задачу в колонку первого шага процесса.

Код в исходной спеке: `R-AP-02`.

**Consequences (testable):**
- Создана задача типа: когда создаётся задача типа «Исследование», первый шаг процесса — колонка «R&D» с агентом «Ресёрчер», тогда задача в колонке «R&D», делегат — «Ресёрчер», запуск в очереди.
- Смена типа: когда тип задачи меняют на тип с процессом, тогда задача переходит на первый шаг нового процесса, активный запуск прежнего шага отменяется.
- Тип без процесса: когда создаётся задача типа без процесса, тогда работает обычная доска: задача без делегата, переходы вручную.

#### FR-190: Эффект Действия «делегировать агенту»

Движок Действий SHALL поддерживать эффект, назначающий агента делегатом задачи.

Код в исходной спеке: `R-AP-03`.

**Consequences (testable):**
- Действие по метке: когда на задачу ставят метку «нужен ревью» и действие делегирует агенту «Ревьюер», тогда делегат — «Ревьюер», запуск в очереди.
- Условие не выполнено: когда метка не поставлена, тогда действие не срабатывает.
- Агент отключён: когда Действие ссылается на выключенного агента, тогда запуск не создаётся, ошибка в истории задачи.

#### FR-191: Приоритет правил

При нескольких применимых правилах ICPlan SHALL выбирать агента в порядке: явный делегат в запросе → агент шага процесса → эффект Действия. Явный делегат — выбор пользователя в поле «Делегат» карточки задачи в любой момент или при переводе; при смене делегата активный запуск прежнего агента по задаче MUST отменяться.

Код в исходной спеке: `R-AP-04`.

**Consequences (testable):**
- Шаг и Действие: когда задача входит в шаг с агентом Y, и Действие по метке даёт агента Z, тогда делегат — Y.
- Явный делегат: когда пользователь вручную указал делегата при переводе, тогда используется явный делегат, шаг процесса не меняется.
- Делегат из карточки без перевода: когда пользователь выбрал агента Z в поле «Делегат» карточки, задача стоит на шаге с агентом Y, запуска Y нет, тогда делегат — Z, запуск Z в очереди; колонка и шаг задачи не меняются.
- Другой агент посреди шага: когда запуск агента шага Y идёт, пользователь выбрал делегатом агента Z, тогда запуск Y отменён (в истории — «отменено пользователем»), запуск Z на том же шаге в очереди.
- Делегат — человек: когда запуск агента шага идёт, пользователь выбрал делегатом человека, тогда запуск агента отменён, делегат-агент снят, работу ведёт выбранный человек; шаг для этой задачи ручной до следующего входа в шаг.
- Итог запуска явного делегата: когда запуск явного делегата завершился, тогда итог пишется в задачу, перехода по процессу нет: задача остаётся на шаге, её дальше двигает человек или агент шага при следующем входе.
- Только Действие: когда шаг ручной, Действие даёт агента Z, тогда делегат — Z.

#### FR-192: Защита от дублей

ICPlan MUST NOT ставить второй запуск, если у этого агента по этой задаче уже есть запуск в очереди или в работе.

Код в исходной спеке: `R-AP-05`.

**Consequences (testable):**
- Повторный вход в шаг: когда задачу дважды подряд переводят в колонку того же шага, пока запуск активен, тогда в очереди один запуск.
- После завершения: когда задачу снова переводят в колонку шага после завершения запуска, тогда создаётся новый запуск.
- Разные агенты: когда шаг процесса и Действие дают разных агентов, тогда создаётся запуск только по правилу с высшим приоритетом.

#### FR-193: Передача результата следующему этапу

Запуск следующего шага SHALL получать в задании передачу предыдущего (M3: сделано, дальше, ссылки на артефакты, вопросы, предложенные критерии) и ссылку на итог. Предложенные критерии MUST добавляться к задаче с пометкой автора и подтверждаться по `criteria_approval` шага (AD-20).

Код в исходной спеке: `R-AP-06`.

**Consequences (testable):**
- Смена агента: когда шаг агента A завершён успешно и ICPlan перевёл задачу на шаг агента B, тогда задание агента B содержит ссылку на итог агента A.
- Первый этап: когда у задачи нет предыдущих запусков, тогда задание без ссылки на итог.
- Предыдущий запуск упал: когда последний запуск завершился ошибкой, тогда ссылка ведёт на итог с пометкой ошибки.
- Критерии от предыдущего шага: когда аналитик в передаче предложил критерий «есть миграция БД» для шага «Код», у шага `criteria_approval: auto`, проверки нет, тогда критерий добавлен с пометкой «предложено: Аналитик» и действует для запуска разработчика.
- Подтверждение на шаге с проверкой: когда у следующего шага `criteria_approval: review` или включена проверка, тогда предложенный критерий ждёт подтверждения человеком до старта шага.

#### FR-194: Видимость подхвата

Каждый автоподхват и каждый переход процесса SHALL записываться в историю задачи с указанием правила (шаг процесса, Действие) и итога запуска.

Код в исходной спеке: `R-AP-07`.

**Consequences (testable):**
- Разбор: когда пользователь открывает историю задачи, тогда видит «Агент Y взял задачу: процесс "Фича", шаг "Анализ"».
- Переход по итогу: когда запуск завершился успешно и задача перешла на следующий шаг, тогда в истории «Итог: успех → шаг "Спецификация"».
- Ручное делегирование: когда пользователь назначил делегата сам, тогда запись «делегировано пользователем», без правила.

#### FR-195: Очистка при выходе агента из проекта

Когда агент перестаёт работать в проекте, ICPlan SHALL снимать его с шагов процессов и Действий этого проекта; такие шаги становятся ручными. История задач с результатами агента MUST сохраняться.

Код в исходной спеке: `R-AP-08`.

**Consequences (testable):**
- Агента убрали из проекта: когда у агента сняли проект, тогда шаги процессов проекта больше не ссылаются на агента, они ручные; Действия проекта «делегировать агенту» с ним выключены.
- Активные запуски при снятии проекта: когда у агента сняли проект, а по задачам этого проекта у него есть запуски в очереди или в работе, тогда интерфейс предупреждает о числе активных запусков; после подтверждения они отменяются, делегат снят, задачи остаются на своих шагах.
- История сохраняется: когда у агента сняли проект, тогда комментарии, итоги и записи «агент взял / закончил» в истории задач проекта (`issue_activity`) остаются.
- Агент удалён: когда агент удалён из команды, тогда ссылки на него сняты во всех проектах.
- Удаление агента с активными запусками: когда администратор удаляет агента, у которого есть активные запуски, тогда интерфейс предупреждает о числе активных запусков; после подтверждения запуски отменяются, шаги процессов с этим агентом становятся ручными, Действия «делегировать агенту» с ним выключаются.
- Агент остался в проекте: когда у агента сняли другой проект, тогда правила этого проекта не меняются.

#### FR-196: Определение процесса

Процесс SHALL задаваться в настройках проекта для типа задачи как упорядоченный список шагов. Шаг: колонка проекта, агент (необязательно), переход при успехе (следующий шаг, другой процесс или «завершить»), переход при ошибке (шаг или «остаться»), лимит запусков на шаге. ICPlan MUST NOT сохранять процесс с ошибкой структуры. Шаг MAY задавать «результат шага», «готовность шага» и `criteria_approval` (`auto` / `review` / `always`) — контракт шага (AD-20).

Код в исходной спеке: `R-AP-15`.

**Consequences (testable):**
- Корректный процесс: когда администратор сохраняет процесс «Фича»: R&D (Ресёрчер) → SDD (Аналитик) → Код (Разработчик) → Ревью (человек) → завершить, тогда процесс сохранён, у каждого шага одна колонка и явные переходы.
- Ошибка структуры: когда переход ведёт на несуществующий шаг, колонка повторяется в процессе или шаг недостижим от первого, тогда сохранение отклонено с указанием шага и причины.
- Переход в другой процесс: когда у последнего шага процесса «Исследование» переход при успехе — процесс «Фича», тогда при успехе тип задачи меняется на «Фича», задача встаёт на первый шаг процесса «Фича».
- Готовность шага: когда у шага «SDD» задана готовность «есть разделы Проблема, Требования, Критерии», тогда этот критерий получает каждая задача на шаге с пометкой «процесс», без чек-листа человека.
- Декомпозиция — дочерние задачи: когда агенту шага нужно разбить задачу на части, тогда он создаёт дочерние задачи тулом `create_issue`, у каждой свой тип и свой процесс; сам процесс задач не создаёт.
- Один переход при успехе: когда администратор задаёт шагу два перехода при успехе, тогда сохранение отклонено: параллельные работы делаются дочерними задачами.

#### FR-197: Переход по итогу запуска

После завершения запуска агента на шаге ICPlan SHALL перевести задачу по итогу: успех — по переходу при успехе; ошибка, лимит или непройденный quality gate — по переходу при ошибке с уведомлением владельца процесса; ожидание ответа — задача остаётся на шаге; отмена человеком — без перехода. Агент MUST NOT менять колонку задачи сам: он возвращает итог, переход делает ICPlan.

Код в исходной спеке: `R-AP-16`.

**Consequences (testable):**
- Успех: когда агент «Аналитик» на шаге SDD завершил запуск успешно, тогда задача переходит на шаг «Код», делегат — «Разработчик», в его очереди запуск.
- Ошибка: когда запуск на шаге «Код» упал или не прошёл quality gate, тогда задача — по переходу при ошибке (например, «Нужна помощь»), делегат снят, исполнитель — владелец процесса, уведомление.
- Лимит запусков на шаге: когда задача входит в шаг «Код» в четвёртый раз при лимите 3, тогда запуск не создаётся, задача — по переходу при ошибке с причиной «лимит шага».
- Агент пытается сменить колонку: когда агент вызывает `update_issue` со сменой колонки задачи, которая идёт по процессу, тогда смена колонки отклонена, остальные поля обновлены.
- Ждёт ответа: когда запуск на шаге завершился итогом «ждёт ответа» (вопрос пользователю или approve), тогда задача остаётся в шаге, исполнитель получает уведомление, запуск продолжается после ответа.
- Отменено пользователем: когда пользователь отменил запуск на шаге, тогда перехода нет, делегат снят, в истории задачи — «отменено пользователем».

#### FR-198: Очередь агента

У каждого агента SHALL быть очередь запусков по всем процессам, где он исполнитель шага. Runner SHALL забирать запуск из головы очереди: порядок — приоритет задачи, затем время постановки; запуск выдаётся одному Runner с арендой, у задачи не более одного активного запуска.

Код в исходной спеке: `R-AP-17`.

**Consequences (testable):**
- Порядок очереди: когда в очереди агента задача «срочно» поставлена позже задачи «обычный», тогда Runner получает сначала задачу «срочно».
- Задача уже в работе: когда задача уже имеет активный запуск, тогда второй запуск по ней не выдаётся, пока первый не завершён.
- Runner пропал с арендой: когда Runner взял запуск и перестал отвечать, тогда по истечении аренды запуск снова доступен в голове очереди.

#### FR-199: Проверка пользователем перед переходом

Шаг процесса SHALL иметь настройку «нужна проверка», а задача — флаг «проверять со мной» для всех её шагов. После успешного запуска на таком шаге ICPlan SHALL оставить задачу на шаге в состоянии «ждёт проверки», уведомить исполнителя и MUST NOT переводить задачу до вердикта.

Код в исходной спеке: `R-AP-18`.

**Consequences (testable):**
- Шаг с проверкой: когда агент шага «SDD» с настройкой «нужна проверка» завершил запуск успешно, тогда задача остаётся на шаге «SDD» в состоянии «ждёт проверки», исполнителю уведомление.
- Флаг на задаче: когда у задачи включён флаг «проверять со мной», шаг без проверки, тогда после каждого успешного шага задача ждёт вердикта.
- Нет вердикта: когда вердикта нет дольше `review_reminder_hours`, тогда повторное уведомление, задача не двигается.

#### FR-200: Вердикт по результату

Исполнитель или владелец процесса SHALL выносить вердикт по результату шага: «принято» — ICPlan выполняет переход при успехе; «не выполнено» с обязательной заметкой — новый запуск того же шага, заметка в задании. Возврат MUST учитываться в лимите запусков шага. Ревьюер (агент или человек) MAY добавить критерий при возврате; он сохраняется с пометкой автора (AD-20).

Код в исходной спеке: `R-AP-19`.

**Consequences (testable):**
- Принято: когда пользователь отметил результат шага «Код» как «принято», тогда задача переходит по переходу при успехе.
- Не выполнено: когда пользователь отметил «не выполнено» с заметкой «нет тестов», тогда новый запуск агента шага «Код», заметка в задании и в истории задачи.
- Лимит возвратов: когда возврат превышает лимит запусков шага, тогда переход при ошибке с причиной «лимит шага», уведомление владельцу процесса.
- Нет прав: когда вердикт выносит не исполнитель и не владелец процесса, тогда действие недоступно.
- Ревьюер добавил критерий: когда агент-ревьюер возвращает задачу «не выполнено» и добавляет критерий «покрыть тестами», тогда критерий добавлен с пометкой «ревьюер», следующий запуск исполнителя проверяется и по нему.

#### FR-201: Остановка и возобновление процесса по задаче

Пользователь SHALL останавливать процесс по задаче: активный запуск отменяется, входы в шаги не создают запусков, ручные переводы разрешены. Возобновление SHALL запускать агента текущего шага. Остановленная задача MUST быть видна в сводке и истории.

Код в исходной спеке: `R-AP-20`.

**Consequences (testable):**
- Остановка: когда пользователь остановил процесс задачи во время запуска на шаге «Код», тогда запуск отменён, Runner узнаёт об отмене по heartbeat, новые запуски не создаются.
- Ручной перевод: когда остановленную задачу перевели в колонку шага с агентом, тогда запуск не создаётся, в истории «процесс остановлен».
- Возобновление: когда пользователь возобновил процесс, тогда запуск агента текущего шага.

#### FR-202: Повтор шага

Пользователь SHALL повторять шаг (новый запуск того же шага с итогом прошлого запуска в контексте) и перезапускать задачу с выбранного шага (обычный вход в шаг). Повтор сверх лимита запусков шага MUST быть доступен только владельцу процесса и сбрасывать счётчик шага.

Код в исходной спеке: `R-AP-21`.

**Consequences (testable):**
- Повтор после ошибки: когда шаг «Код» завершился ошибкой, пользователь нажал «повторить шаг», тогда новый запуск агента шага, итог ошибки в задании.
- С выбранного шага: когда пользователь выбрал «начать с шага SDD», тогда задача в колонке шага SDD, запуск его агента, счётчики следующих шагов сброшены.
- Лимит исчерпан: когда лимит запусков шага исчерпан, повтор просит исполнитель, тогда повтор недоступен, предложение обратиться к владельцу процесса.

#### FR-203: Изменение процесса

Изменение процесса SHALL создавать новую версию, действующую для новых переходов; активные запуски доделываются на шаге, где начались. Удаление шага, на котором стоят задачи, MUST требовать указать шаг, куда их перенести (как сопоставление статусов при публикации workflow).

Код в исходной спеке: `R-AP-22`.

**Consequences (testable):**
- Новая версия: когда администратор изменил переход шага «Код» при задачах в работе, тогда задачи после текущего шага идут по новой версии.
- Удаление шага с задачами: когда администратор удаляет шаг, на котором стоят 3 задачи, тогда сохранение требует выбрать шаг для переноса; без выбора не сохраняется.
- Активный запуск на изменённом шаге: когда агент шага изменён во время запуска, тогда запуск доделывает прежний агент, следующий вход — новый.

#### FR-204: Триггеры запуска ICPlan

ICPlan SHALL ставить запуск агента в очередь при: назначении делегатом (с задержкой `delegation_delay_sec`), упоминании в комментарии, срабатывании расписания агента, изменении поля-триггера, ручном запуске. Автоназначение колонки SHALL менять только исполнителя и MUST NOT создавать запуск. Это базовое поведение ICPlan, на нём строится процесс.

Код в исходной спеке: `R-AP-23`.

**Consequences (testable):**
- Делегирование: когда пользователь назначил агента делегатом задачи, тогда через `delegation_delay_sec` запуск доступен раннеру, триггер `delegation`.
- Упоминание: когда в комментарии упомянут агент, тогда запуск с триггером `mention`, ответ — в ветке комментария.
- Автоназначение колонки: когда задача вошла в колонку с автоназначением человека, тогда исполнитель сменён, запуск не создаётся.

#### FR-205: Переходы по причинам

Шаг процесса SHALL задавать переходы `transitions[{reason, to}]`: причина из справочника (`done`, `defect`, `spec_question`, `blocked`) и цель — шаг процесса, человек или завершение; `onSuccess` и `onFailure` остаются переходами по умолчанию. Агент шага SHALL выбирать исход запуска (`outcome`, а при возврате `returnTo` и `returnNote`) только из переходов, разрешённых для шага; исход вне списка MUST отклоняться, запуск считается ошибкой шага. Причина «вопрос правил или спеки» (`spec_question`) SHALL вести к шагу — владельцу знания или к человеку, но не к соседнему шагу без источника. Возврат MUST учитываться в лимитах FR-206; колонку задачи по-прежнему меняет только ICPlan. R&D, AD-27.

Код в исходной спеке: `R-AP-24`.

**Consequences (testable):**
- Исход из разрешённых: когда агент шага «Проверка» завершил запуск с исходом `defect` и `returnTo = code`, а в `transitions` шага есть `defect → code`, тогда задача возвращается на шаг «Код», `returnNote` попадает в задание нового запуска и в историю задачи.
- Исход вне разрешённых: когда агент вернул исход, которого нет в `transitions` шага, тогда переход не выполняется, запуск завершён ошибкой шага с причиной «недопустимый исход», уведомление владельцу процесса.
- Вопрос правил или спеки: когда агент шага «Код» вернул исход `spec_question`, тогда задача идёт к шагу, владеющему знанием (например, «SDD»), а если такого шага нет в `transitions` — к человеку (исполнитель — владелец процесса, уведомление).
- Вердикт человека сохраняется: когда человек вынес вердикт «не выполнено» по шагу, к которому вернулась задача, тогда вердикт и заметка не перезаписываются исходом агента (FR-200).

#### FR-206: Лимиты цепочки

Процесс SHALL ограничивать цепочку по задаче: `maxRuns` шага (FR-197), общее число запусков `maxTotalRuns` по задаче и признак «нет прогресса» — круг переходов, после которого нет нового результата (нового артефакта, изменённого критерия или нового коммита). При срабатывании любого лимита запуск MUST NOT создаваться, задача идёт по переходу при ошибке с причиной («лимит задачи» или «нет прогресса»), владелец процесса получает уведомление. Значения по умолчанию задаются в `interfaces.md` с пометкой «пересмотр по замеру (agent-chain.md, ворота G9)». AD-27.

Код в исходной спеке: `R-AP-25`.

**Consequences (testable):**
- Лимит запусков задачи: когда по задаче уже `maxTotalRuns` запусков, а процесс требует ещё один, тогда запуск не создаётся, переход при ошибке с причиной «лимит задачи», уведомление владельцу процесса.
- Нет прогресса: когда задача прошла круг «Код → Проверка → Код», а нового результата между запусками нет, тогда следующий запуск не создаётся, переход при ошибке с причиной «нет прогресса».
- Повтор сверх лимита вручную: когда владелец процесса нажал «повторить шаг» после срабатывания лимита задачи, тогда создаётся один запуск, попытка помечена как ручная и в историю записан автор.

#### FR-207: Независимая проверка перед завершением

Процесс по умолчанию SHALL содержать шаг-проверку перед завершением задачи: агент и запуск проверки MUST быть другими, чем у исполнителя, проверка идёт по критериям приёмки шага (AD-20). Процесс из одного шага (один агент) остаётся допустимой базовой линией; отключить проверку MAY владелец процесса явной настройкой. AD-27.

Код в исходной спеке: `R-AP-26`.

**Consequences (testable):**
- Шаг-проверка по умолчанию: когда создан процесс с шагом исполнителя и без настройки проверки, тогда перед завершением задача проходит шаг-проверку другим агентом (или человеком), а не завершается по итогу исполнителя.
- Проверяющий совпадает с исполнителем: когда в процессе агент шага-проверки совпадает с агентом исполнителя, тогда сохранение процесса отклонено с ошибкой, называющей шаги.
- Один агент без проверки: когда владелец процесса явно отключил проверку и оставил один шаг, тогда процесс сохраняется как базовая линия, в метриках (FR-152) помечается «один шаг».

#### FR-208: Конфигурация модуля

Модуль SHALL брать свои параметры (14, таблица «Параметры модуля» в `interfaces.md`) с уровней L2 (S1), L3 (S1), L0 (S9): значение — с самого конкретного уровня; значение вне границ «Мин»–«Макс» таблицы MUST отклоняться с ошибкой, называющей параметр и границы. Изменение настройки SHALL действовать со следующего запуска; обязательные поля MUST проверяться при сохранении.

Код в исходной спеке: `R-AP-09`.

**Consequences (testable):**
- Значение по умолчанию: когда `step.agent` (агент шага (пусто — ручной шаг)) не задан в настройках, тогда применяется значение по умолчанию: нет.
- Выше максимума: когда `step.max_runs` задан больше 10, тогда значение отклонено, ошибка называет `step.max_runs` и границы 1–10.
- Нет обязательного поля: когда настройку сохраняют без `process.issue_type`, тогда сохранение отклонено, ошибка называет `process.issue_type`.

#### FR-209: Хранилища данных

Модуль SHALL хранить свои данные только в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) (`interfaces.md`). Секреты MUST NOT храниться в БД и git.

Код в исходной спеке: `R-AP-10`.

**Consequences (testable):**
- Запись в своё хранилище: когда модуль сохраняет процессы и шаги (`process`, `process_step`), флаги задач, Действия,…, тогда запись попадает в S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`).
- S1 недоступно: когда S1 (PostgreSQL 17 (CloudNativePG), БД `itsaplan`) не отвечает, тогда итог не принимается и остаётся у Runner, который повторяет отправку (FR-17); переход по итогу выполняется, когда итог принят.
- Доступ вне своих хранилищ: когда код icplan-agent-autopickup обращается к таблицам вне S1, тогда доступа нет: роль БД icplan-agent-autopickup ограничена S1.

#### FR-210: Интерфейсы обмена

Интерфейсы модуля (I20, I1) SHALL соблюдать протокол, формат, аутентификацию, таймаут и политику повтора из `interfaces.md`; неидемпотентные вызовы MUST NOT повторяться автоматически.

Код в исходной спеке: `R-AP-11`.

**Consequences (testable):**
- Таймаут I1: когда ICPlan Run Queue → Agent Runner (I1) не ответил за 10 с, тогда вызов прерывается; повтор: backoff до 60 с.
- Права по I20: когда пользователь без права изменения меняет процессы и шаги (`process`, `process_step`), флаги задач, Действия, история переходов, тогда API ICPlan отклоняет запрос (403), данные не меняются, событие в журнале.
- Повтор I1 без дублей: когда вызов I1 повторён после сбоя, тогда дубля нет: аренда запуска: выдаётся одному Runner.

#### FR-211: Поведение при отказах зависимостей

Модуль SHALL вести себя при отказах зависимостей по таблице FMEA (`interfaces.md`): отказ обнаруживается, поведение предсказуемо и безопасно (fail-closed для проверок безопасности), восстановление не теряет данные.

Код в исходной спеке: `R-AP-12`.

**Consequences (testable):**
- Агент правила не участник проекта: когда агент правила не участник проекта, тогда запуск не создаётся, предупреждение в истории.
- Очередь недоступна: когда постановка запуска в очередь не удалась, тогда делегат установлен, worker ICPlan повторяет постановку с backoff до 60 с (как повторы I1), не более 5 попыток; не удалось — запись в истории задачи «запуск не поставлен» и уведомление владельцу процесса.
- Восстановление после неудачной постановки: когда 5 попыток постановки не удались, очередь снова доступна, тогда сам запуск не ставится: владелец процесса или исполнитель нажимает «повторить шаг» (FR-202), создаётся один запуск; попытка постановки не считается в `step.max_runs`.
- Цикл переходов: когда задача входит в шаг в (`step.max_runs` + 1)-й раз, тогда запуск не создаётся, задача — по переходу при ошибке с причиной «лимит шага», уведомление владельцу процесса.

#### FR-212: Развёртывание

Модуль SHALL разворачиваться так: часть api / worker ICPlan (`itsaplan-core`). Ресурсы MUST задаваться requests / limits, версии образов — закреплены; публичный доступ — только через ingress, если он указан.

Код в исходной спеке: `R-AP-14`.

**Consequences (testable):**
- Установка в составе ICPlan: когда разворачивается релиз ICPlan (часть api / worker ICPlan (`itsaplan-core`)) с модулем icplan-agent-autopickup, тогда миграции icplan-agent-autopickup применены до старта `api`, модуль доступен в ICPlan.
- Обновление: когда выходит новая версия форка ICPlan с изменениями icplan-agent-autopickup, тогда миграции icplan-agent-autopickup обратно совместимы, `api` обновляется по одной реплике без простоя.
- Откат: когда версия с изменениями icplan-agent-autopickup не прошла проверки готовности, тогда Helm откатывает ревизию, данные icplan-agent-autopickup сохранены.
